# 設計書: 摩天楼 (Matenro) (MC6809 + 差し替え可能なサブ CPU)

## 1. 目的と範囲

富士通 FM-11 の「マンハッタンシステム」のように、**異種 CPU を 1 つのメモリに密結合**したマシンのシミュレータです。

* メイン CPU は MC6809 で、OS は **OS-9 Level 2** です。6809 側のメモリ、MMU、I/O は **sim09 に準拠**しています
  (`/export/nas/archives/MC6809/new-sbc09` の `src/` を元にしています。元のディレクトリは参照しただけで、変更していません)。
* サブ CPU は **8 ビットデータバスの CPU を 1 ファイルで差し込める**ようにしてあります。いま入っているのは **Z80** と **8088** です。
* 2 つの CPU は**物理 RAM を共有**し、それぞれ**自分の最大クロック**で、同時に動きます。
* ストレージは SD カード相当 (ディスクイメージ。生のデバイス `/dev/sdX` も指せます) で、6809 側 (OS-9) だけが持ちます。
  サブ CPU はディスクを直接は触らず、共有メモリとメールボックス経由で 6809 (OS-9) に頼みます (マンハッタンの方式と同じ考え方)。
* **Z80 では CP/M-80、8088 では CP/M-86 のプログラムが、OS-9 のコマンド `cpm` から動きます** (12 章)。
* **FPGA 版 (Tang Nano 9K、6809 + Z80) は実機で動いています** (15 章、[FPGA.md](FPGA.md))。8088 は 9K に載らないので、シミュレータだけです (20K のボードが要ります)。

> **FM-11 の再現ではありません。** FM-11 のマンハッタンシステムの資料やコードは見ていません。「異種 CPU がメインメモリを
> 共有する」という考え方だけを借りて、レジスタ構成を新しく設計しました。

## 2. 全体構成

```
                       +--------------------------------------------+
   OS-9 Level 2        |  物理 RAM 2MB  (8KB x 256 ブロック)         |
   +---------+  MMU    |  [0 ............ memsize) [memsize ..2MB)    |
   | MC6809  |-------->|   OS-9 が使う RAM          サブ CPU 用プール |
   | 2 MHz   |  XC_SHR |                                  ^          |
   +----+----+ (任意)  +----------------------------------|----------+
        |  I/O ページ $FF80                                | SMMU (128 x 8KB)
        |   $FFC9-$FFCD  XLINK レジスタ                     |
        +-----------------+                          +-----+------+
                          | ドアベル / メールボックス |  サブ CPU   |
                          +------------------------->| Z80 / 8088  |
                                                     | 8 MHz       |
                                                     +-------------+
   SD カード (ディスクイメージ) --- 6809 の I/O ($FFC0-$FFC8, sim09 のまま) だけ
```

図のクロックはシミュレータの既定値です。FPGA 版では 6809 が E = 1.875 MHz、Z80 が 7.5 MHz です (15 章)。

## 3. サブ CPU の差し込み口 (`subcpu.h`)

CPU は `sub_cpu_ops_t` を 1 つ公開するだけです。マシンのほかの部分には触りません。

```c
typedef struct sub_bus {                 /* CPU から見たバス (マシンが渡す) */
    void *ctx;
    uint8_t (*mem_read)(void *ctx, uint32_t addr);   /* addr は addr_bits ビット */
    void    (*mem_write)(void *ctx, uint32_t addr, uint8_t v);
    uint8_t (*io_read)(void *ctx, uint16_t port);    /* 下位 8 ビットだけ使う */
    void    (*io_write)(void *ctx, uint16_t port, uint8_t v);
    uint8_t (*int_ack)(void *ctx);                   /* 割り込み受け付けサイクルのバイト */
} sub_bus_t;

typedef struct sub_cpu_ops {
    const char *name; const char *desc;
    int      id;            /* XID レジスタの値 (Z80=1, 8088=2) */
    int      addr_bits;     /* 16 / 20 */
    uint32_t max_hz;        /* そのグレードの最大クロック */
    void *(*create)(const sub_bus_t *bus);  void (*destroy)(void *);
    void  (*reset)(void *);
    int   (*step)(void *);                  /* 1 命令 (または割り込み受け付け / HALT 中の 1 スロット)、使ったクロック数を返す */
    void  (*set_line)(void *, int line, int level);   /* SUB_INT (レベル) / SUB_NMI (エッジ) */
    int   (*is_halted)(void *);  int (*int_pending_ok)(void *);
    uint32_t (*pc)(void *);  uint64_t (*insn_count)(void *);  void (*dump)(void *, FILE *);
} sub_cpu_ops_t;
```

**新しい CPU を足すには**: `src/xxx.c` を書いて `const sub_cpu_ops_t sub_cpu_xxx` を公開し、`subcpu.h` に `extern` を 1 行、
`xlink.c` の `registry[]` に 1 項目、`Makefile` の `SRC` に 1 ファイルを足すだけです (8 ビットバスの CPU なら 6502、6800、
8085、V20/V30 などが候補)。

### 3.1 Z80 (`src/z80.c`)

* 公式の命令すべて、IXH/IXL、`DD CB d op` のレジスタへのコピー、`SLL`、`IN F,(C)`、`OUT (C),0`、X/Y フラグ、MEMPTR (`WZ`)、
  割り込みモード 0/1/2、NMI、`EI` の 1 命令遅れ、HALT。T ステートは Zilog のマニュアルどおり (命令ごとの固定値)。
* 実装していないもの: バス要求/ウェイト、`INIR/OTIR` 系と繰り返しブロック命令の X/Y フラグの細かい副作用。
* 最大クロック: **8 MHz** (Z80H)。CMOS の Z84C00 は 20 MHz まであるので、`-subclock 20000000` で変えられます。

### 3.2 8088 (`src/i8088.c`)

* 8086/8088 の命令すべて (プレフィックス、文字列命令と `REP` (反復ごとに割り込み可能)、`MUL/IMUL/DIV/IDIV`、BCD 補正、
  `INT/INTO/IRET`、トラップフラグ、`STI` と `MOV SS` の割り込み 1 命令遅れ、0 除算)。8086/8088 の未定義の動き
  (`60-6F` が `70-7F` の別名、`C0/C1/C8/C9`、`82`、シフトの `/6`、`SALC`、`POP CS`) も実機どおりにしてあります。
  80186 以降の命令 (`PUSH imm`、`PUSHA` など) は**ありません**。
* クロック数は、8086 マニュアルの実行ユニットのクロック数に EA 計算を足し、**16 ビットの転送 (データ、スタック、ベクタ) 1 回ごとに
  4 クロックを足した**値です (8088 の 8 ビットバスの規則)。**プリフェッチキューとバスインターフェースユニットは作っていない**ので、
  命令フェッチで律速されるコードでは実機より速く出ます。
* 最大クロック: **8 MHz** (8088-2)。

## 4. メモリの考え方

### 4.1 物理 RAM

物理 RAM は **2MB** (8KB のブロックが 256 個) です。レベル 2 の 6809 の MMU (sim09 のまま: 8KB × 8 ページ × 2 タスク、
ブロック番号 8 ビット) が見るのはこの RAM です。

| 名前 | 内容 |
|---|---|
| `-m サイズ` (`memsize`) | **6809 (OS-9) が使える RAM**。既定は sim09 と同じ 2MB (全部)。`-m 1M` にすると下半分だけです |
| `memsize` から 2MB まで | **サブ CPU 用のプール**。6809 の MMU からは見えません (読むと `$FF`、書いても消える)。6809 は XLINK の**ウィンドウ**で触ります。`XC_SHR` を立てると MMU からも見えて、直接共有できます |

サブ CPU は、全部の 2MB を見られます (OS-9 が使っている RAM も)。**OS-9 とサブ CPU が同じブロックを取り合わない**ようにするのは
ソフトウェアの役目です: `-m 1M` で OS-9 を下半分に閉じ込めて、上半分 (ブロック `$80`-`$FF`) をサブ CPU が使う、というのがいちばん簡単です。
OS-9 の中でブロックを確保するドライバ `xlink` があり、これを使えば `-m` なしの 2MB のマシンのままで動きます (14 章)。

### 4.2 SMMU (サブ CPU のメモリ管理)

サブ CPU のアドレス空間は **8KB ブロック 128 個 (1MB)** に区切られ、各ブロックが物理 RAM のブロック (8 ビット) に写されます。
Z80 は先頭の 8 個 (64KB)、8088 は 128 個全部 (1MB) を使います。6809 の MMU と同じ作りです。

* リセット後の割り当ては `ブロック i → 物理ブロック (xbase + i)`。`xbase` の既定は `$80` (物理 `$100000` から。8088 の 128 ブロックで
  ちょうど上半分 1MB)。`-xbase` で変えられ、6809 側から `XE_MI`/`XE_MD` で書き換えられます。
* 6809 の I/O ページ (物理 `$7FE00`-`$7FFFF`) は RAM ではないので、サブ CPU からは読むと `$FF`、書くと無視されます。
* 範囲外 (物理 2MB より上) も読むと `$FF`、書くと無視されます。
* Z80 は `PC=0000` から、8088 は `CS:IP=FFFF:0000` (= 線形 `FFFF0` = ブロック 127 の末尾) から始まります。6809 側で、
  そこに最初の命令 (8088 なら `JMP FAR`) を置いてからサブ CPU を動かします (`os9/xrun.asm` がやっています)。

## 5. sim09 からの変更点

| 場所 | 変更 |
|---|---|
| `machine.h` `machine.c` | 物理 RAM を常に 2MB に (`physsize`)、6809 が見える範囲を `mainlimit` に (`memsize` または `XC_SHR` のとき `physsize`)。IRQ/FIRQ を**タイマとドアベルの OR** で決める `machine_update_irq()`。XLINK レジスタの I/O 振り分け。`machine_run` にサブ CPU の追従 (`xlink_catch_up`) と、追従中の時間刻み (`quantum`) の制限。パワーレジスタ (`$FF8F`) に `$A6` (終了コード 1) と `$A7` (再起動、`machine_reboot`) を追加 |
| `main.c` | `-sub -subclock -xbase -xload -xrun -xt -xcon -xquantum -L1`。既定が Level 2。6809 のクロックの既定が 2 MHz (sim09 は 1.8432 MHz) |
| それ以外 (`m6809.c` `dis6809.c` `console.c` `net.c` `vdisk.c` `dbg.c`) | 無変更 |

OS-9 Level 2 の ROM とディスクイメージ (`new-sbc09/os9/`) は**そのまま**動きます (`tests/matenro_test.py` が起動を確かめます)。

## 6. XLINK: 6809 側のレジスタ

I/O ページ (`$FF80` から) の $49-$4D、つまり **`$FFC9`-`$FFCD`** の 5 バイトです。sim09 の Level 2 の I/O ページは
`$FFD0`-`$FFFF` が OS-9 のベクタページ (コードとデータ) で、`$FFC0`-`$FFC8` がディスクなので、空いているのはここだけです。
そのため、**直接のレジスタ 3 つと、索引 + データの対**にしました。

| アドレス | 名前 | 読み | 書き |
|---|---|---|---|
| `$FFC9` | `XCTL` | 制御 | 制御 |
| `$FFCA` | `XSTAT` | 状態 | **ACK**: サブ CPU からのドアベルを消す (値は何でもよい) |
| `$FFCB` | `XID` | サブ CPU の種類 (0 = なし、1 = Z80、2 = 8088) | **ドアベル**: サブ CPU を呼ぶ (bit 7 = 1 なら NMI) |
| `$FFCC` | `XIDX` | 拡張レジスタの索引 | 同左。**bit 7 = 1 で `XDAT` に触るたびに索引が +1** |
| `$FFCD` | `XDAT` | 拡張レジスタのデータ | 同左 |

> **`XDAT` に読み書き命令 (`CLR` `INC` `ASL` など) を使わないでください。** 6809 のこれらの命令は先に 1 回読むので、
> 自動加算が余分に進みます。`LDA` / `STA` を使います。

> **FPGA 版 (`fpga/rtl/xlink.v`) の約束**: 索引のデコードと、ウィンドウアドレスの桁上げは、それぞれ 1 クロックずつ遅れて有効になります (長い経路を切るため。FPGA.md の 9.6)。`XIDX` を書いてから (または自動加算のあと) 次の `XDAT` に触るまで 1 クロック以上あけてください。6809 は 1 バスサイクルが 18 クロック以上なので、ふつうの命令列では必ず守られます (テストベンチは自分で 1 クロックあけます)。ウィンドウ (`XE_WD`) の読み書きは、終わるまで 6809 のクロックを止めます (`m_wait`)。

`XCTL`:

| bit | 名前 | 意味 |
|---|---|---|
| 0 | `XC_RUN` | 0 = サブ CPU をリセットしたままにする。0 → 1 でリセットが外れる (CPU は最初から) |
| 1 | `XC_HOLD` | 1 = サブ CPU を止める (バスホールド) |
| 2 | `XC_SHR` | 1 = 6809 の MMU から、`memsize` より上のプールも見える |
| 3 | `XC_FIRQ` | サブ CPU → 6809 の割り込みに FIRQ を使う (0 = IRQ) |
| 4 | `XC_IEN` | サブ CPU → 6809 の割り込みを許可 |
| 7 | `XC_RESET` | 書くとサブ CPU のリセットを 1 回かける (読むと 0) |

`XSTAT`: bit0 `XS_S2M` = サブ CPU がドアベルを鳴らして 6809 がまだ ACK していない、bit1 `XS_M2S` = 6809 がドアベルを鳴らしてサブ CPU が
まだ ACK していない、bit2 `XS_HALT` = サブ CPU が HALT/HLT 中、bit3 `XS_RUN` = 動いている。

拡張レジスタ (`XIDX` の下位 7 ビット):

| 索引 | 名前 | 内容 |
|---|---|---|
| `$00`-`$03` | `XE_M2S` | メールボックス: 6809 → サブ CPU (6809 は読み書き、サブ CPU は読むだけ) |
| `$04`-`$07` | `XE_S2M` | メールボックス: サブ CPU → 6809 (6809 は読むだけ) |
| `$08` | `XE_MI` | SMMU の索引 (0-127) |
| `$09` | `XE_MD` | SMMU のデータ: サブ CPU のブロック `XE_MI` が写る物理ブロック |
| `$0A`-`$0C` | `XE_WA` | ウィンドウのアドレス: **物理** アドレス (21 ビット、上位バイトから) |
| `$0D` | `XE_WD` | ウィンドウのデータ: 読み書きするたびにウィンドウのアドレスが +1 |
| `$0E`-`$0F` | `XE_KHZ` | サブ CPU のクロック (kHz、上位バイトから) |
| `$10`-`$13` | `XE_CLK` | サブ CPU の実行したクロック数 (`$10` を読んだ瞬間の値を保持、上位バイトから) |
| `$14`-`$17` | `XE_US` | リセットからのマイクロ秒 (`$14` を読んだ瞬間の値を保持、上位バイトから。71 分で一周)。FPGA 版はシステムクロックの実時間 (6809 が止まっても進む)、シミュレータは 6809 の時間 (サイクル数 ÷ クロック)。OS-9 のコマンド `etime` が使う |

6809 から共有メモリへの入り口は 2 つあります。**(a) ウィンドウ** (`XE_WA`/`XE_WD`): 物理アドレスで、どんな OS・どんな MMU の設定でも
使えます (OS-9 のユーザプロセスからも)。**(b) 直接の共有**: `XC_SHR` を立てて、6809 の MMU のエントリにサブ CPU のブロックの
物理ブロック番号を書けば、普通のメモリとして読み書きできます。

## 7. サブ CPU 側のポート

I/O ポートの**下位 8 ビット**を見て、`$00`-`$0F` だけが有効です (Z80 の `OUT (n),A` の A、8088 の `OUT DX` の上位は無視)。

| ポート | 読み | 書き |
|---|---|---|
| `$00` | サブ CPU の種類 (`XID` と同じ) | |
| `$01` | 状態: bit0 = 6809 がドアベルを鳴らした (未 ACK)、bit1 = 自分のドアベルが未 ACK、bit7 = 1 | |
| `$02` | | **ドアベル**: 6809 を呼ぶ (`XS_S2M` が立ち、`XC_IEN` なら IRQ/FIRQ) |
| `$03` | | **ACK**: 6809 のドアベルを消す (INT 線が下がる) |
| `$04`-`$07` | メールボックス 6809 → サブ CPU | |
| `$08`-`$0B` | メールボックス サブ CPU → 6809 | 同左 |
| `$0C` | 割り込み受け付けで返すバイト (Z80 の IM 2 のベクタ、IM 0 の命令、8088 のベクタ番号)。既定 `$FF` | 同左 |
| `$0E` | | デバッグコンソール: 1 バイトをホストへ出す (`-xcon file`、既定は stderr) |
| `$0F` | | `$A5` = シミュレータを終了 (コード 0)、`$A6` = 終了 (コード 1)。テスト用。**`$A7` = 再起動** (OS-9 の `reboot`): シミュレータは RAM を消して ROM イメージを読み直し、CPU・サブ CPU・タイマを初期化する (ディスクとコンソールはそのまま)。FPGA 版は S1 を押したのと同じ全体リセット (`tn9k_top` の電源投入時リセットの計数をやり直す) |

6809 → サブ CPU のドアベルは **INT 線をレベルで立てます** (サブ CPU が ACK するまで)。NMI は `XID` への書き込みの bit 7 で 1 回だけ
パルスを出します。

### 7.1 割り込み線の系統図

割り込みの源は 3 つで、6809 に行くもの 2 つ (タイマ、サブ CPU のドアベル) と、サブ CPU に行くもの 1 つ (6809 のドアベル) です。FPGA の信号名は FPGA.md 9.10 にあります。

```
   サブ CPU (Z80 / 8088)                    XLINK                                      6809
   ---------------------      ----------------------------------------      ------------------------

   OUT $02 (ドアベル) ------> pend_s2m (XSTAT bit0) ---+
                                                       |  AND XCTL.IEN (bit4)
              XSTAT への書き込み (ACK) で消える ------>|
                                                       v
                                       XCTL.FIRQ (bit3) = 0 --------------------> IRQ  --+
                                       XCTL.FIRQ (bit3) = 1 --------------------> FIRQ    |  (xlink_main_irq)
                                                                                          |
   タイマ (50 Hz、timer_pending) ---------------------------------------------> IRQ  -----+--> OR
     tick で立つ、割り込み受け付け (iack) で消える                                        |  (machine_update_irq)
                                                                                          v
                                                                                   OS-9 のカーネル
                                                                                     D.SvcIRQ (Clock)
                                                                                     時計の割り込みでなければ D.Poll
                                                                                     -> F$IRQ の表 -> xlink ドライバ

   INT 線 <------- pend_m2s (XSTAT bit1) <------ XID への書き込み (bit7 = 0) <---- 6809 (ドアベル)
   (レベル)          消える: OUT $03 (ACK)、XCTL の RESET

   NMI 線 <------- 1 回だけのパルス <----------- XID への書き込み (bit7 = 1) <---- 6809 (NMI)
```

* 6809 への線は、IRQ と FIRQ のどちらも**タイマとサブ CPU の OR**です (`machine_update_irq`)。Level 2 の OS-9 はタイマを IRQ で使い、`XCTL` の FIRQ ビットは 0 のままにします。
* サブ CPU への INT は**レベル**で、ACK するまで立ち続けます。NMI は**パルス**です。
* `XCTL.IEN` が 0 のとき、6809 は `XSTAT` を見る (ポーリング) だけでドアベルを知ります。IEN が 1 の間だけ IRQ になります (ドライバは `SS.XWait` で眠る間だけ立てます、14 章)。
* ソフトウェアの受け口: Z80 は IM 1 の RST 38h (`duo` のワーカー)。IM 2 や 8088 は `$0C` のバイトをベクタとして使います。6809 は Clock モジュールが `D.Poll` で `F$IRQ` の表を調べて、`xlink` ドライバへ渡します。

## 8. スケジューリング (同時に動く 2 つの CPU)

* 6809 は sim09 のとおり `m6809_run()` で、サブ CPU は `step()` で、どちらも**命令単位**で動きます。
* 時刻は**ピコ秒**で数えます。6809 は `total_cycles × 周期`、サブ CPU は `t_ps += クロック数 × 周期` です。周期は `10^12 / Hz` (整数)。
* 6809 が (最大 `quantum` = 16 サイクル ≒ 8µs) 進むたびに、サブ CPU を**6809 の時刻まで追いつかせます** (`xlink_catch_up`)。
  したがって、2 つの CPU の見え方のずれは最大でも 1 命令 + `quantum` 程度で、**毎回同じ結果になります** (決定的)。
* サブ CPU が HLT で割り込み待ちのときは、時間を進めるだけで命令を回しません。6809 も SYNC/CWAI で待っているときは、sim09 の
  「アイドルスキップ」でどちらも時間を飛ばします。
* 実時間に合わせる (`-max` なし) ときは、sim09 と同じく 6809 のクロックに合わせます。
* メモリの競合 (同時アクセスのウェイト) は、シミュレータでは**作っていません**。FPGA 版では PSRAM を調停回路 (`psram_arb4.v`) で共有するので、
  6809、Z80、ウィンドウ、ディスクが実際に順番を待ちます (15 章、[FPGA.md](FPGA.md))。

## 9. ストレージ (SD カード)

sim09 のディスクのまま: `$FFC0` に `$81` (読み) / `$55` (書き) を書くと、256 バイトのセクタを DMA します。ディスクイメージは
ファイルでも、SD カードの生のデバイスでも構いません (`-0 /dev/sdX`、書き込みに注意)。FPGA 版の `sd_disk.v` (SPI モードの SD カード、
512 バイトのブロックに 2 セクタ) もこの仕様です。ハードディスクにもフロッピーにも使え、OS-9 の RBF の `d0`/`d1` ドライバがそのまま使えます。

サブ CPU がディスクを使うには、6809 (OS-9) が**サーバ**になります: サブ CPU が共有メモリに要求を書いてドアベルを鳴らし、OS-9 の
プロセスが読み書きして、ドアベルで知らせます。この要求・応答の約束事の一例が、CP/M の BDOS 呼び出し用の要求ブロックです (12 章)。ディスクのセクタを直接頼む汎用の約束事は決めていません (11 章)。

## 12. CP/M-80 と CP/M-86 のプログラムを OS-9 から動かす (`cpm` コマンド)

OS-9 のシェルから `cpm ファイル [引数]` と打つと、サブ CPU が CP/M のプログラムを**そのまま**実行します。

| サブ CPU | ファイル | 例 |
|---|---|---|
| Z80 (`-sub z80`) | CP/M-80 の `.COM` | `cpm hello.com abc` |
| 8088 (`-sub 8088`) | CP/M-86 の `.CMD` (8080 モデル、スモールモデル) | `cpm hello86.cmd abc` |

**方式**: サブ CPU は BDOS の呼び出し (Z80 は `CALL 5`、8088 は `INT E0h`) を実行すると、共有メモリの**要求ブロック**に関数番号と引数を書いて
ドアベルを鳴らし、返事を待ちます。6809 側の OS-9 プロセス `cpm` がドアベルに気づき、**OS-9 のシステムコールで**コンソール入出力とファイル操作を
して、結果を要求ブロックに書きます。つまり、**OS-9 が CP/M の BDOS の役を引き受ける**マンハッタン方式で、CP/M の CCP/BDOS/BIOS の
バイナリは使いません (入手していません)。ファイルは OS-9 のファイルそのもので、`cpm` を起動したときのデータディレクトリにあります。

### 12.1 要求ブロック (共有メモリ)

| オフセット | 内容 |
|---|---|
| +0 | 関数番号 (C / CL) |
| +1, +2 | 引数 DE / DX (下位、上位) |
| +4, +5 | DS (8088 のみ。FCB や文字列の場所はこの DS と DX から決まる) |
| +8 | 結果 A / AL |
| +9, +10 | 結果 HL / BX (下位、上位) |
| +11 | 結果 AH (8088) |
| +12 | **完了フラグ**: サブ CPU が 0 にしてからドアベルを鳴らし、6809 が最後に 1 を書く。サブ CPU はこれが 0 でない間、メモリを見て待つ |

要求ブロックの場所は Z80 が `FC80h`、8088 が `0000:0600` です。サブ CPU の側のスタブは `os9/cpm/z80shim.asm` と `os9/cpm/i8088shim.asm`
(`os9/cpm/mkshims.py` が `fcb` データにして `cpm.asm` に埋め込みます)。6809 → サブ CPU の割り込み (`XID` へのドアベル) は**使いません**
(完了フラグで待つので、プログラムが `EI`/`STI` していても余計な割り込みが入りません)。

### 12.2 メモリの使い方

* **Z80**: `0000` にゼロページ (`JP START`、のち `JP WBOOT`、`IOBYTE`、`CALL 5` 用の `JP BDOS`、`005C`/`006C` の FCB、`0080` のコマンドテールと
  既定の DMA)、`0100` から TPA に `.COM` を読み込む。`FC00h` から**スタブ** (BDOS = `FC06`、**BIOS の入口の表 = `FC2D`〜`FC5F`**、要求ブロック = `FC80`、`START` = `FCC0`)。`LD HL,(6)` で見えるメモリの上限は `FC06h` なので、
  TPA は約 63KB です。アドレス 1 (ウォームブートの入口) は `FC30` を指すので、BIOS の表を `(1)` から計算するプログラム (Turbo Pascal) も動きます (12.6)。プログラムの `RET` は `0000` に戻り、ウォームブートとして扱います。
* **8088** (CP/M-86): INT `E0h` のベクタ (`0000:0380`) が `0000:0500` のスタブを指す。起動コード `0000:0540`、プログラムが `RETF` で終わったときの
  終了スタブ `0000:0580`、要求ブロック `0000:0600`、起動情報 `0000:0620`。8080 モデルは `1000:0000` にベースページ、`1000:0100` からコード (CS = DS = ES = SS = `1000h`)。
  スモールモデルはコードグループを `1000:0000` に、データグループを `2000:0100` に読み込む (DS = ES = SS = `2000h`、ベースページは `2000:0000`)。
  `SP = FFFAh`、スタックには終了スタブへの戻り番地を積む。リセットベクタ (`FFFF:0000` = 線形 `FFFF0`) に `JMP FAR 0000:0540` を置く。

### 12.4 制約

* **BDOS レベルの互換**です。CP/M の CCP、BDOS、BIOS の実物は動かしておらず、BIOS のディスクの入口 (SELDSK、READ、WRITE など) を直接呼ぶプログラム、
  CP/M-86 の関数 50、ディスクのセクタを直接読むプログラム (`STAT` の一部、`SYSGEN` など)、割り当て表を使うプログラムは動きません。
* ワイルドカードの名前の変更、SYS とアーカイブの属性、`^C` で中断する処理 (この OS-9 の端末は、`^C` を割り込みとして扱いません)、`^S` `^P` は未対応です。ディレクトリの検索の
  レコード数は 128 までです。
* CP/M のファイル名は大文字ですが、OS-9 は大文字小文字を区別しないので、同じファイルに当たります (作ったファイルの名前は大文字になります)。
* サブ CPU は BDOS の返事を**ビジーウェイト**で待ちます。6809 側も短いビジーウェイトのあと `F$Sleep` で待ちます。
* 同時に動かせるのは 1 つのサブ CPU だけなので、Z80 の `.COM` と 8088 の `.CMD` は、それぞれ `-sub z80`、`-sub 8088` で起動したときに動きます。
* `cpm` が使うメモリ (サブ CPU のプール) と OS-9 のメモリは、ドライバ `xlink` (14 章) を `load` してあれば OS-9 が自分で分けます。ドライバがないときは `-m 1M` で分けます。
* 実物の CP/M ソフトでの検証は、(1) Z80 の命令セットを調べる ZEXDOC (67 項目)、(2) HI-TECH C の各パス (13 章)、(3) Turbo Pascal 3.0 (12.6 章)、(4) Digital Research の `STAT` `ASM` `LOAD` `PIP` `ED` `DDT` と `MBASIC` 5.21 (試験 `os9_cpmapps`、`MATENRO_CPM`) で行いました。
  どれもこのリポジトリには入れていません (ライセンスと再配布の都合)。それ以外はこのプロジェクトで書いた小さなテストプログラム (下) です。
  実物を動かして見つけた不具合: `STAT` は BDOS 18 (検索の続き) を `DE=0` で呼ぶ (FCB は使わない: 検索の最初のドライブを覚える)、MBASIC の `SAVE` はトークン形式 (先頭が FFh) で、`.BAS` を無条件にテキストと見ると壊れる (先頭の 1 バイトで見分ける)。
* Z80 のスタックを `LD HL,(6)` から始めるプログラム (HI-TECH C など) は、`FC06h` の下 6 バイトに最初の `PUSH` を書きます。スタブの WBOOT をそこ (`FC00h`)
  に置くと壊れるので、WBOOT は `FC30h` にあり、`FC00h`〜`FC05h` は空けてあります。

### 12.6 BIOS の入口と Turbo Pascal

CP/M の BIOS の入口は、`(1)` の指す先 (WBOOT) の前後に 3 バイトずつ並んだジャンプ表です (BOOT、WBOOT、CONST、CONIN、CONOUT、LIST、PUNCH、READER、HOME、SELDSK、…、SECTRAN の 17 個)。
Turbo Pascal 3.0 は、コンソールの入出力に BDOS ではなく **BIOS の CONST / CONIN / CONOUT** を直接呼びます (`LD HL,(1)` で表を探して `JP (HL)`)。スタブにこの表がないと、`FC39h` (CONOUT) に飛んで
`START` まで滑り、プログラムが最初から再起動し続けました。

| 入口 | 動き |
|---|---|
| BOOT, WBOOT | プログラムの終了 (BDOS 0) |
| CONST | キーがあれば `FFh`、なければ `0` (BDOS 6 の状態と同じ。標準入力がファイルのときは「キーなし」) |
| CONIN | キーを 1 つ待つ (エコーなし) |
| CONOUT | `C` の文字を出す (変換なし) |
| READER | `1Ah` |
| それ以外 (LIST、PUNCH、HOME、ディスク系) | 何もしない。`A` と `HL` は 0 (SELDSK は「ディスクなし」) |

各入口は、要求ブロックの関数番号 `80h + 表の番号` と、パラメータ `BC` を 6809 に渡します (`cpm.asm` の `bios`)。

**端末**: BIOS のコンソールを最初に使ったとき、`cpm` は標準入力の OS-9 の端末を**生入力**にします (エコーなし、大文字化なし、CR のあとの改行なし、`^C` `^E` `^W` を捨てずに通す。**ESC も通す**: OS-9 の端末は ESC (`1Bh`) を既定でファイルの終わりの文字 `PD.EOF` として扱い、読むと EOF エラーを返すので、無効にします。
Turbo Pascal の「`File not found. Press <ESC>`」などの ESC が効かなくなるためです)。
Turbo Pascal のエディタは WordStar のキー (`^K` `^S` `^E` など) を使うためです。プログラムが終わると元の設定に戻します (`cleanup`)。

**Turbo Pascal 3.01A (CP/M-80)** はこのリポジトリに入っていません (ライセンス)。付属の `TURBO.COM` は別の端末向けに設定してあるので、`TINST` で `ANSI` を選び直します
(画面の設定 `S` → 端末 `6` (ANSI) → 変更しない `N` → CPU の周波数 → 終了 `Q`。`Q` で終わらないと `TURBO.COM` に書かれません)。
動かした範囲: ソースの読み込み (`W`)、編集 (`E`、`^KD` で抜ける)、コンパイル (メモリ、`.COM`)、実行、保存 (`S`: 古いファイルは BDOS 23 で `.BAK` になる)、ディレクトリ (`D`)、終了 (`Q`)。
`.PAS` と `.INC` はテキストファイルとして扱います。`TURBO.MSG` `TURBO.OVR` は `cpm -p=dir` で探せる場所に置きます。
TP は画面を描いている間に来たキーを読み捨てるので、自動操作では描き終わりを待ちます。試験は `tests/matenro_test.py` の `os9_turbo` (`MATENRO_TP` に `TURBO.COM` `TURBO.MSG` `TURBO.OVR` のあるディレクトリを渡したときだけ)。

### 12.5 テスト

`tests/matenro_test.py` が、OS-9 Level 2 を起動して `cpm` を実行します。テストプログラムは Z80 用が `tools/z80asm.py` (自作の小さなアセンブラ) で、8088 用が
`nasm` (`cpu 8086` で 8086 に無い命令を禁止) と `tools/mkcmd.py` (`.CMD` ヘッダを付ける) で作ります。

## 13. シームレスな操作: OS-9 のプリプロセッサ → CP/M-80 の C コンパイラ

目標は「OS-9 側で作ったツールと CP/M 側のツールを、ひとつの作業として続けて使える」ことです。例として、C のソースを OS-9 で作ったプリプロセッサに通し、
CP/M-80 の C コンパイラ (HI-TECH C 3.09) でコンパイルして、できたプログラムを `cpm` で動かします。

```
OS-9 (6809)    cpp  prog.c  ->  prog.i                          os9/cpp/cpp.asm (6809 のアセンブラで書いた C プリプロセッサ)
CP/M-80 (Z80)  p1 prog.i prog.p1, cgen prog.p1 prog.as          cpm が Z80 で動かす
CP/M-80 (Z80)  zas -> prog.obj, linq (+ crtcpm.obj libc.lib) -> prog.com
OS-9 -> Z80    cpm prog.com
```

`cc80` (`os9/cc80/cc80.asm`) がこの順に `F$Fork` で起こします。`cc80 -r -v prog.c` で、コマンドを表示しながらコンパイルして実行します
(`-s` `-c` で `.as` `.obj` で止める、`-k` で途中のファイルを残す、`-t=dir` でコンパイラの場所を変える、`-D` `-I` は `cpp` へ渡す、`-lf` で浮動小数点のライブラリ `libf.lib` を `libc.lib` の前につける)。
`float` を使うプログラムは `-lf` が要りますが (元のドライバの `-LF`)、`cc80` は `cgen` の出力 `file.as` を見て、浮動小数点のルーチンの呼び出し (`call fladd` `flmul` `aitof` など) があれば自分でつけます。
HI-TECH C は、元のドライバ `C309.COM` が `$EXEC` で次のパスを起こす作りで、`cpm` の上では動かなかったので、各パスの引数 (元のドライバが作る
`$$EXEC.$$$` と OPTIONS から読み取ったもの) を `cc80` が直接並べます。

### 13.1 `cpp` (OS-9 のプリプロセッサ)

`#include` (`"..."` と `<...>`、4 段まで)、`#define` (引数あり/なし)、`#undef`、`#ifdef` `#ifndef` `#if` `#elif` `#else` `#endif`、`#error`、`#line` `#pragma` (捨てる)、
式 (`defined` `?:` `||` `&&` `|` `^` `&` `==` `!=` `<` `>` `<=` `>=` `<<` `>>` `+` `-` `*` `/` `%` `!` `~`、10 進/16 進/8 進/文字定数)、
コメントと行の継ぎ足し (`\`)、文字列の中を展開しない、引数を先に展開してから置き換える (C の規則)、再帰の防止 (展開中のマクロは展開しない)。
`#` (文字列化) と `##` (連結) は関数形式マクロの中で使えます (引数は `#` `##` の隣では展開しない原文を使います)。オブジェクト形式マクロの `##` は未対応です。出力の行末は CR (OS-9 のテキスト) で、`cpm` が CP/M へ渡すときに CR LF に変えます。`-ofile` で結果をファイルに書きます。

マクロは 64 本のハッシュ表 + 一列のヒープ (6000 バイト) に置き、置き換えの途中結果は展開の深さ (7 段) ごとのバッファ、引数は深さごとの引数ブロックに置きます。
`#if` の式は 16 ビット符号付きの再帰下降パーサです。作った途中で見つけた間違い (レジスタの上書き 5 件ほか) は `tests/cpp/*.c` で防いでいます。

### 13.2 `cpm` に足したもの

* `-p=dir`: プログラムと、現在のディレクトリに無いデータファイル (`crtcpm.obj` `libc.lib` など) を探すディレクトリ。
* `-k`: コマンドテールを大文字にしない (CP/M の CCP は大文字にしますが、HI-TECH C のパスは `-Ptext=...` のように大文字小文字を区別します)。
* `-b`: 拡張子による判定をやめて全部をバイナリ扱いにする。 `-d`: BDOS 呼び出しを標準エラー出力に出す。
* テキストファイル (`.C` `.H` `.I` `.AS` `.TXT` など) は OS-9 の CR と CP/M の CR LF + ^Z を相互に変換します。プログラムが閉じずに終わったファイルは、終了時に閉じて
  一時ファイル (`$CPMTn`) を消します。
* `STDIN` `STDOUT` `STDERR` という名前のファイルは OS-9 の標準入出力に結び付くので、`list a.txt ! cpm filter ! ...` のようにパイプやリダイレクトに使えます。
* 前のプログラムが残したdoorbell (XSTAT) を起動時に捨てます。残っていると、次の `cpm` が最初に「古い要求 (関数 0)」を受けて、すぐ終わってしまいました。

## 14. OS-9 のデバイスドライバ (`xlink`、デスクリプタ `x0`)

シミュレータでも、FPGA の実機でも、同じドライバが動きます (実機では `cpm hello.com`、`bstress`、`cc80`、ZEXDOC をこのドライバの上で動かしました)。

これまでは `-m 1M` で OS-9 を下半分に閉じ込め、上半分 (物理 `0x100000` から) をサブ CPU が使う運用でした。ドライバは、**サブ CPU のメモリを OS-9 自身の空き RAM から借りる**ので、OS-9 は 2MB 全部を持つ普通のマシン (`-m` なし) のままで済みます。

| ファイル | 内容 |
|---|---|
| `os9/xlink/xlink.asm` | ドライバ (SCF 用のエントリ表。ハードウェアのアドレスはデスクリプタの `$FFC9`) |
| `os9/xlink/x0.asm` | デスクリプタ `x0` (`/x0` で開く。マネージャは SCF) |

* **Init** (`/x0` を最初に開いたとき): `XID` を見て (0 や `$FF` は「サブ CPU なし」でエラー)、`F$AlHRAM` で RAM の**上の方**から連続したブロックを取ります。Z80 は 8 ブロック (64KB)、8088 は 32 ブロック (256KB)。そのブロックを SMMU に書きます (`XE_MI` / `XE_MD`): サブ CPU のブロック *i* → 取ったブロック + *i*、取った数より後ろの 128 ブロック目までは**最後のブロック**へ向けます (8088 のリセットベクタ `FFFF0h` が 127 番目のブロックにあるため)。
* **Term** (最後に閉じたとき): サブ CPU を止め (`XCTL = 0`)、`F$DelRAM` でブロックを返します。
* **GetStat** `$B0` (SS.XInfo): `R$A` = XID、`R$X` = 先頭の物理ブロック、`R$Y` = ブロック数。`$B1` (SS.XWait): サブ CPU のdoorbellを待つ。`R$X` = タイムアウト (tick、0 は 100)。`R$A` = 1 (doorbellあり) / 0 (タイムアウト)。
* `cpm` と `duo` は起動時に `/x0` を開きます。開けたら (ドライバが `load` してあれば) doorbell待ちを `F$Sleep` 1 tick のポーリングから SS.XWait にします。開けなければ従来どおり (`-m 1M` の運用) です。SMMU を介して番地を決めている (`setwin`) ので、`cpm` のほかの部分は変わっていません。

```
OS9:chx /v0/cmds
OS9:load xlink
OS9:load x0
OS9:cpm hello.com abc           -m なしの 2MB のマシンで動く
```

**割り込みで起こします** (`IRQMODE equ 1`。ドライバは `F$IRQ` の割り込み表に入る)。それには Clock モジュールが、タイマ以外の割り込みで `D.Poll` (割り込み表を調べる処理) を呼ぶ必要があります。sim09 の元の `clock.asm` は、どの IRQ も時計の tick として数え、`D.Poll` を呼びませんでした。直したところ (`os9/level2/clock.asm`、new-sbc09 側): (1) タイマのレジスタの bit 4 が立っていなければ時計の割り込みではないので、`D.QIRQ` を `$FF` にして (カーネルはすぐ戻る) `D.Poll` を呼ぶだけの処理にする、(2) 時計の割り込みのときも `D.Poll` を呼ぶ (同時に来たドアベルを取りこぼさない)。この処理は NitrOS-9 の `mc09clock.asm` と同じ形です。ドライバは割り込みを許可 (XCTL bit 4) するのを `SS.XWait` で眠る間だけにして、割り込みを受けたら許可を下ろします。`SS.XInfo` は受けた割り込みの数を `R$U` で返します (`duo -i` で見られる)。

Z80 側 (`duo` のワーカー) は、HALT で待ち、6809 のドアベルの割り込み (IM 1、RST 38h) で行を計算します。ROM が増えたので、`l2boot.asm` と `mkl2disk.py` (new-sbc09 側) の読み込む区画数を 105 から 106 にし、ROM イメージの置き場所を LSN 720 から **LSN 1100** に移しました。理由: 720〜825 はベースディスクのファイル (`OS9Boot` など) がある領域で、`mkl2disk` がコマンドを入れ替えるとき、削除で空いた 825 番を新しいコマンドが再利用して ROM の最後の区画を上書きしていました (105 区画のときは 825 番に触れなかった)。起動領域が 0x4903 バイトを超えると、末尾のモジュール (D0 など) が壊れて `/d0` が見えなくなりました (Error #221)。

テスト (`make test-mh`): Z80 で `hello` と `fileio` と `hello` を続けて (取る・返すを繰り返す)、8088 で `hello86` と `small86` を、`-m 1M` なしで動かします。`cc80` も、ドライバを `load` した状態で 2 回続けて通りました (手動で確認、自動テストはドライバなし)。

### 手順ファイルの中の `cc80` (`shell <file`) と、システムメモリ (2026-10-31)

実機で `shell </d1/loop` (中身は `cc80 -t=/d1/htc -r hello.c` の繰り返し) を動かすと、1 回目の `linq` が `libc.lib: Can't open` で失敗し (`Not enough memory to run.` も出る)、そのあと動かなくなりました。シミュレータ (`/d1` を 2 番目のディスクにして) で再現でき、原因は 2 つでした。

1. **システムメモリ不足**: `I$Attach` の `F$SRqMem` が `$CF` (メモリ満杯) で失敗していました。OS-9 Level 2 のシステムメモリは小さく (トレースで約 6.3KB が上限付近)、パスを 1 つ開くたびに 256 バイトのページを 1 つ使います (`F$SRqMem` は 256 バイト単位)。`linq` は同じファイル (`LIBC.LIB` を 1 回に 2 つ、`CRTCPM.OBJ`、`HELLO.OBJ`) を何度も開き、CP/M のプログラムは読むだけのファイルを閉じないので、`cpm` のパスが溜まります。プロンプトから呼んだときは収まりますが、`shell` の子プロセス (プロセス記述子 512 バイトなど) が加わると足りなくなります。**直し**: `cpm` は、いま開いているファイルと同じ名前を開くとき、同じ OS-9 のパスを使い回します (`shtab`、6 件、`shfind` `shadd` `shdrop`)。読み出しは毎回レコード位置へシークするので FCB 同士は干渉せず、閉じるのは最後の FCB のときだけです。`BDOS` の make と delete は、その名前の登録を捨てます。
2. **手順ファイルを食べる**: HI-TECH のプログラムは終了時などにキーが押されたかを BDOS 6 (`E = 0FFH`) と 11 で調べます。`cpm` は準備ができていれば 1 バイト読むので、標準入力が手順ファイルだと**その中身を読み捨てて**、シェルが 2 行目以降を失いました。**直し**: 標準入力が RBF のファイルのとき (`stdrbf`) は「キーなし」を返します (キーボードとパイプは今までどおり)。

試験: `tests/cpm/kbpoll.asm` と `share.asm`、`cc80` を手順ファイルから 2 回呼ぶ試験 (`MATENRO_HTC` が要ります)。1. のメモリ不足は、`/d1` (RBF) に HI-TECH C を置いたときだけ起きるので、自動試験 (`/v0` はメモリを食わない) では出ません。`fpga/tn9k/scripts/mkdisk_d1.sh` のイメージを使うシミュレータで、直さないと失敗し、直すと 3 回とも通ることを確かめました。

| | シミュレータ | FPGA 版 |
|---|---|---|

| サブ CPU | Z80 と 8088 | Z80 だけ (8088 は 9K の LUT に載らない) |
| メモリ競合 | なし | PSRAM の調停で実際に待つ |
| ホストのファイル (`/v0`) | あり | なし (SD カードのイメージだけ) |
| 時計 | ホストの時刻 | 電池なし (ビルドした時刻から数える) |
| 画面 | 端末 | UART (115200 baud) だけ。HDMI なし |
| 起動 | すぐ | 電源投入時に PSRAM の検査 (55、AA、アドレス) を約 4.5 秒 (`Memory >>>> OK 2048K`) してから消去。`MEMTEST=0` で省ける |

**タイミング**: 67.5 MHz で収めています。一番長い経路を短くして、setup の余裕は +0.011 ns から +0.326 ns になりました (FPGA.md の 9.6)。そのために XLINK は、索引のデコードと窓アドレスの桁上げを 1 クロック遅らせています (6 章の約束)。実機は、ツールのモデルより 10% 速い 74.25 MHz でも動きました (FPGA.md の 9.4)。

```
fpga/tn9k/scripts/mkdisk.sh OUT.dsk                              # SD カードのイメージ (/d0)

```

## 16. OS-9 のプログラムから BDOS を呼ぶ (サブルーチンモジュール `bdos`)

6809 の OS-9 のプログラムが、CP/M の BDOS を**関数番号で**呼べます (`CALL 5` の `C` = 関数番号、`DE` = パラメータ)。Z80 は使いません。`cpm` と**同じエンジン**で、ゲストのメモリの代わりに、呼んだプログラム自身のメモリを使います。FCB、文字列、DMA バッファは、呼び出し側のメモリに置いたものを指します。

**方式**: `cpm.asm` を、BDOS の実装 (`cpmengine.asm`) と Z80 用の部分 (`cpm.asm`: 起動、要求ブロックのやりとり、プログラムの読み込み) に分けました。エンジンがゲストのメモリに触るのは `rdsub` / `wrsub` の 2 つの関数だけなので、
`cpm` はこれを「サブ CPU の窓」に、`bdos` は「呼び出し側のメモリ」に向けています。直した不具合は両方に効きます。`bdos.asm` はサブルーチンモジュール (`Sbrtn`) で、エンジンの作業領域 (約 2.3KB) は**呼び出し側が用意**して `Y` で渡します (`BDOSSZ` バイト)。

| 項目 | 内容 |
|---|---|
| 呼び出し | `F$Link` で `bdos` を探し (`U` にモジュールのアドレスが返るので、データポインタを退避する)、返った `Y` (入口) を覚えて、`jsr [入口,u]` |
| 入力 | `A` = 関数番号、`X` = `DE`、`Y` = 作業領域 |
| 出力 | `A` = CP/M の `A`、`X` = `HL`、`B` = `H`。`U` は保たれる |
| 特別な関数 | `$FF` = 初期化 (作業領域を消す。最初に 1 回)、`$FE` = 終了 (開いたままのファイルを閉じ、テキストファイルを書き戻す。プログラムが終わる前に) |
| 関数 | `cpm` と同じ (12 章): コンソール 1 2 6 9 10 11、バージョン 12、ファイル 15 16 17 18 19 20 21 22 23 26 33 34 35 36 |
| ファイル名 | OS-9 のカレントのデータディレクトリ。テキストファイルの変換 (`.TXT` `.C` `.PAS` など) も `cpm` と同じ |
| コンソール | 呼び出し側の標準入出力 (BIOS の入口は使わない) |
| スタック | 呼び出し側のスタックを約 400 バイト使う |

使い方の全体は `os9/bdos/bdos.d` に、動く例は `tests/bdos/bdostest.asm` (`bdostest`: ファイルを作って、書いて、名前を変えて、読んで、消す) にあります。DMA アドレスは関数 26 で決めるまで 0 です。
`cpm` と違って、ゲストの `0080h` にあたる領域はありません。

試験: `make test-mh` の `bdos module` の 1 項目。

## 17. 実機のマシンサイクルでシミュレーションする (設計と、段階(a)の 6809・段階(b)の Z80・段階(c)の 8088 まで実装、2026-11-03)

**目的**: C のシミュレータの時間を、実機 (FPGA) の時間に合わせる。今は 6809 が名目どおり (1 サイクル = E の 1 周期)、Z80 は命令表の T 数だけで進み、メモリを待ちません。実機は 6809 も Z80 も PSRAM の応答を待つので遅く、`duo` の時間はシミュレータより実機のほうが長くなっています。

| `duo` の時間 | シミュレータ (今) | 実機 | 比 |
|---|---|---|---|
| 6809 だけ (`-1`) | 5.64 s | 7.48 s | 1.33 |
| Z80 だけ (`-z`) | 10.6 s | 18.08 s | 1.70 |
| 二つ (6809 17〜18 行、Z80 7〜8 行) | 4.1 s | 5.9 s | 1.4 |

### 17.1 実機の仕組み (RTL から)

* PSRAM のコントローラは一度に一つのアクセスしかできません (`psram_arb4.v`)。マスタは 0 = 6809 とディスクと起動、1 = HDMI の変換、2 = HDMI の表示 (締切があるので最優先)、3 = Z80。一つのアクセスに約 19 クロック (システムクロック 67.5 MHz)。
* 6809 (`matenro_soc.v`): E の周期は 36 クロック。PSRAM のアクセスのあいだ CPU を止め (`mem_pend`)、さらに読んだデータが ALU を通り抜けるまで 6 クロック止める (`settle`)。XLINK の窓 (`xl_wait`) とディスク (`disk_busy`) と ACIA (`acia_pend`) でも止まる。
* Z80 (`z80_sub.v`): Z80 のクロックは 9 クロックごとに 1 回 (7.5 MHz)。メモリ読み出しの開始と書き込みの終わりで要求を出し、応答 (`mem_ack`) までと、その後 5 クロック、クロックを止める。つまり**メモリのアクセスごとに、約 19 + 5 = 24 クロック (Z80 の約 2.7 T) の待ち**が入ります (命令の取り出しも同じ)。I/O ポートは待ちなし。

### 17.2 シミュレータの作り方 (バスサイクル単位)

1. **PSRAM のモデル**を一つ作る (`machine.c`): 一度に一つのアクセス、1 アクセスの長さ (クロック数)、マスタの優先順位、起こした時刻と終わる時刻。6809 と Z80 の**両方**がこれを通る。時刻は 67.5 MHz のクロック (ps) で管理する。
2. **Z80** (`z80.c`): 今は 1 命令を 1 ステップで実行し、T 数を返す。これをバスサイクル単位にする: 命令の中の各メモリ読み出し・書き込み・I/O が、`sub_bus_t` のコールバックの中で、その時刻と待ちを返す (M1 は 4T、メモリは 3T、I/O は 4T。待ちはモデルから)。命令の T 数の表は、バスサイクルの並びから出る (MAME の表を照合に使う。コードは写さない)。
3. **6809** (`m6809.c`): すでにバスサイクルごと。メモリのアクセスをモデルに通して、待ちを足す (E の周期の 36 クロックに対する、PSRAM と `settle` と窓の待ち)。
4. **検証**: 実機と同じ RTL を動かす Verilator のシミュレーション (`fpga/tn9k/sim`) を**正解**にする。短い Z80 / 6809 のプログラムを両方で動かし、経過時間が合うことを確かめる。最後に実機の `duo` / `etime` の時間と比べる (上の表)。
5. **段階**: (a) モデルと 6809 の待ち、(b) Z80 のバスサイクル化、(c) 8088 (BIU: 4T のバスサイクル、6 バイトのプリフェッチ・キュー、実行ユニットとの重なり) は Z80 が終わって承認を受けてから。

### 17.3 決めてあること・未定のこと

* 決定: バスサイクル単位、実機のウェイトを 6809 も再現、Z80 の次に 8088。
* 未定: PSRAM のリフレッシュ (周期があるか) と HDMI のマスタ (表示が有効なときの横取り)。まず HDMI なしの構成 (今の実機) に合わせる。
* 注意: シミュレータの時間が実機の時間に変わるので、既存のテストで時間に依存するもの (`etime` の下限など) は見直す。

### 17.4 段階(a): 6809 の待ち (実装済み、`-hw`)

シミュレータは既定で、実機の 6809 の待ちを入れます (オプション `-hw`。**2026-11-03 から既定**)。`-nohw` で待ちなしの理想的な機械 (6809 は `-clock` の 2 MHz、Z80 は 1 命令 = 1 ステップ) に戻せます。`-hw` のとき `-clock` を指定しなければ、E のクロックは実機の 1.875 MHz (67.5 MHz ÷ 36) です。

**測り方**: RTL (Verilator、`fpga/tn9k/sim`) で試験 ROM `fpga/tn9k/test/timing.asm` を動かしました。XLINK のマイクロ秒カウンタ (`XE_US`、実時間) で、2000 回のループにかかる時間を測ります。

| ループ | 内容 | 時間 (µs / 2000 回) | 1 回あたりの超過 |
|---|---|---|---|
| A | ROM だけ (`leax` `bne`、8 サイクル) | 8563 | 名目どおり (E = 36 クロック、0.533 µs) |
| B | RAM を 1 回読む (`lda $0200`) | 14222 | +10.4 クロック |
| C | RAM に 1 回書く (`sta $0200`) | 14074 | +5.4 クロック |
| D | A のループを RAM に置く | 10201 | 1 命令あたり +27〜29 |
| E | RAM の `NOP` 100 個 × 20 | 3059 | 1 命令あたり +31 |
| F | RAM の `lda #0` 100 個 × 20 | 3059 | E と同じ (長さによらない) |
| G | ROM の `NOP` 100 個 × 20 | 2397 | ほぼ名目どおり |

RTL の仕組みから: 6809 は E のサイクルごとに、RAM のアクセス (E が上がるとき) から約 18 クロックのあいだに PSRAM が答え、さらに 6 クロックの `settle` を待ってから次のサイクルに進みます。孤立した読み出しは、アクセス要求から停止解除まで 26 クロック (E のサイクルの開始から 46 クロック = 名目より +10)、書き込みは 21 クロック (+5) でした (`mem_pend` と `stall` を RTL で観測)。RAM にあるコードの命令の取り出しは、これらの単純な足し算より大きくなります (約 +31)。原因までは解明していません (opcode の取り出しの前後で停止が二度かかる、と見ています)。

**モデル** (`machine.c` の `hw_wait`): RAM (Level 2 では I/O ページ以外すべて、Level 1 では ROM と I/O 以外) の読み出しに +10.4 クロック、書き込みに +5.4、命令の最初の 1 バイトを RAM から取るとき +34 (オペランドのバイトは足さない)。クロックは 67.5 MHz のシステムクロック (14815 ps)。足した時間は `stall_ps` に貯め、`machine_time_ps` (Z80 の追いつきと `XE_US` が使う時間) に加えます。`total_cycles` (実行した E のサイクル) は増やさないので、タイマは実機と同じく実行したサイクルを数えます。

**検証**: `duo -1` (6809 だけ) は、シミュレータ 5.64 s (2 MHz) → `-hw -clock 1875000` で **7.43 s** (実機 7.48 s、差 −0.6%)。命令の取り出しの係数 (34) はこの `duo -1` に合わせて決めました (微小ループの測定値は約 29〜31)。

**まだ入れていないもの**: 6809 と Z80 が PSRAM を取り合う競合 (段階(b)で Z80 と一緒に)、XLINK の窓の待ち (`xl_wait`)、ディスクと ACIA の待ち。

### 17.5 段階(b): Z80 の待ちと PSRAM の競合 (実装済み、`-hw`)

**測り方**: 6809 の試験 ROM `fpga/tn9k/test/timing6809.asm` が Z80 のベンチマーク `zbench.asm` を読み込んで動かし、`XE_US` で各ループの時間を測ります (RTL の Verilator)。ループは 2000 回 (L0 = `DEC DE` `LD A,D` `OR E` `JR NZ`、L1〜L5 は L0 に 8 命令を足したもの)。

| ループ | 時間 (µs) | 名目 (7.5 MHz) からの超過 |
|---|---|---|
| L0 (4 回の取り出し + オペランド読み 1 回) | 10939 | 5 回の読み出し × 27 クロック |
| L1 `NOP` ×8 | 25872 | 取り出し 1 回あたり +27 クロック |
| L2 `LD A,(HL)` ×8 | 38672 | 2 回の読み出し → 54 クロック |
| L3 `LD (HL),A` ×8 | 36538 | 取り出し 27 + 書き込み 18 = 45 クロック |
| L4 `INC (HL)` ×8 | 51472 | 27 + 27 + 18 = 72 クロック |
| L5 `LD A,n` ×8 | 38672 | L2 と同じ (読み出し 2 回) |

つまり、**メモリ読み出し (命令の取り出しも) 1 回で 27 クロック、書き込み 1 回で 18 クロック** (システムクロック 67.5 MHz = Z80 の 3 クロックと 2 クロック)、I/O は待ちなし。5 つの値すべてがこれで説明できます (L0 の計算 5.467 µs に対して実測 5.470 µs)。

**モデル** (`machine.c` の `machine_hw_sub_extra`): `xlink_catch_up` が Z80 を 1 命令進めるたびに、その命令の読み出しと書き込みの回数 (`sub_reads` `sub_writes`) に上の待ちを足して Z80 の時間 `t_ps` を進めます (Z80 のクロック数 `XE_CLK` は有効なクロックだけを数えるので変わらない)。命令の中のバスサイクルの順序までは再現せず、命令ごとにまとめて足します (単独の Z80 では結果は同じ)。

**PSRAM の競合**: PSRAM は一度に一つのアクセス。6809 と Z80 のアクセスを直近の 32 回ずつ覚え (`machine_psram_wait`)、他方のアクセスの最中に始まるアクセスは、その終わりまで待たせます。一つのアクセスが PSRAM を使う時間は、`duo` の二つの CPU の時間に合わせて **24 クロック** (PSRAM の約 19 + 解放の 5) にしました。

**検証** (`duo`、既定の `-hw`):

| | シミュレータ (今) | 実機 | 差 |
|---|---|---|---|
| `-1` (6809 だけ) | 7.43 s | 7.48 s | −0.6% |
| `-z` (Z80 だけ) | 18.11 s | 18.08 s | +0.2% |
| 二つ | 5.88 s (6809 18 行、Z80 7 行) | 5.89 s (18 行、7 行) | −0.2%、行の分担も同じ |

**まだ入れていないもの**: 命令の中のバスサイクルの順序、XLINK の窓・ディスク・ACIA の待ち、PSRAM のリフレッシュ (周期があるか未確認)。8088 は段階(c)。

### 17.6 段階(c): 8088 のバスインタフェースユニット (実装済み、`-hw`)

8088 は FPGA にまだなく、**実機でも RTL でも測れません**。そのため基準は Intel の資料 (命令の実行ユニットのクロック数と、8 ビットバスの 4 クロックのバスサイクル、4 バイトのプリフェッチ・キュー) と、この機械の Z80 の待ちです。

**モデル** (`i8088.c`、`-hw` のときだけ): 今までの 8088 は、Intel の表の実行ユニット (EU) のクロック数と、16 ビットの転送ごとの +4 だけで、プリフェッチは見ていませんでした (旧コメント: 命令の取り出しで決まるコードでは楽観的)。`-hw` では、1 命令ごとに:

1. 命令の長さ (取り出したバイト数) だけキューから取り出す。足りなければ EU は待つ: 足りないバイトの数 × 4 クロック − BIU がすでに次のバイトを取りに行っていた分。
2. EU の実行中、バスをデータ転送 (1 バイト 4 クロック) に使っていないクロックで、BIU が 4 クロックに 1 バイトずつキューへ取り出す (最大 4 バイト)。
3. ジャンプ・呼び出し・戻り・割り込みなど、制御が移る命令ではキューを捨てる (Intel の表のジャンプのクロック数には、移った先の最初の 1 バイトの取り出しが含まれているので、キューに 1 バイトある状態から始める)。REP の 2 周目以降は、命令のバイトを取り直さない。

これで、命令が短い (取り出しで決まる) ときは、`NOP` の列が 1 命令あたり 4 クロック (EU の 3 ではない)、`MOV AX,BX` の列が 8 クロック (2 バイトの取り出し) になります。EU が長い命令の後ではキューが満ちているので、次の数命令は EU のクロック数のまま進みます。試験: `tests/i8088_test.c` の「BIU」(`NOP` 40 個が 147 クロック = 先に入っていた 4 バイト + 4 クロックに 1 バイト)。

**PSRAM の待ち**: BIU の実際のバスサイクル (プリフェッチとデータの読み出し・書き込み) の数を `bus_cycles` で受け取り、Z80 と同じ待ち (読み出し 27 クロック、書き込み 18 クロック、他の CPU との競合 24 クロック) を足します。これは**仮定**です: 8088 のラッパー (`z80_sub.v` の 8088 版) が Z80 と同じ作りになる、という前提。

**検証できていないこと**: 8088 の実機と RTL がないので、時間の数字は実機と比べていません。CP/M-86 の試験は `-hw` でも通ります。実機が出来たら、Z80 と同じ方法 (RTL で `XE_US` を使うベンチマーク) で係数を確かめる。

### 17.7 精度の見直しと、タイミングの余裕の最適化 (2026-11-03)

**シミュレータの精度**: 17.4〜17.5 の係数は、微小ループ (RTL で実測) と、そのときのカードの `duo` に合わせたものです。Clock モジュールを替えた (14 章のドアベルの割り込み) 後のカードで測り直すと、RTL (Verilator) と実機は 7.753 s と 7.750 s で一致し、シミュレータだけが離れました。今の差は次のとおりです。

| `duo` | シミュレータ | 実機 | 差 |
|---|---|---|---|
| `-1` (6809 だけ) | 7.38 s | 7.75 s | −4.8% |
| 二つ | 5.85 s | 5.78 s | +1.2% |
| `-z` (Z80 だけ) | 18.45 s | 18.08 s | +2.1% |

つまり**精度は ±5%** で、「1% 以内」は係数をそのときのソフトウェアに合わせた結果でした。6809 の命令ごとの待ち (読み出し + 10.4、書き込み + 5.4、RAM から取る命令 + 34 クロック) は、命令の種類による違いを平均したものです。さらに合わせるには、6809 の命令ごとの RTL での実測が要ります。

**Clock の `D.Poll`**: タイマの 1 tick ごとに `D.Poll` を呼ぶと、6809 が約 6% 遅くなりました (毎秒 50 回、IOMan の表の走査が PSRAM の待ちで 2 倍になる)。外しても、保留中のデバイスの割り込みは tick のあとでもう一度入り、タイマ以外の経路で処理されるので、動作は変わりません。

**タイミングの余裕** (最悪スラック): 最適化前 +0.093 ns (最初の表の先頭は −0.229 ns の PSRAM の経路だが、TNS に入らない) → **+0.451 ns** (Fmax 69.6 MHz)。同じ RTL でも、配置のたびに +0.04〜+0.67 ns とばらつきます (`PLACE=0`〜`3`)。変えたのは、すべて動作のタイミングを変えない、レジスタを挟む変更です:

* 6809 の MMU のマップとモードレジスタの書き込み: 条件を `acc_go` で 1 クロック前にレジスタに取る。
* XLINK の読み書きの合図 (`xl_re` `xl_we`): 同様。
* I/O のデコード (`io_*`) を 2 段に。ディスクのレジスタと他の読み出しデータを 2 段に選ぶ。
* 位相カウンタが見る待ちのうち、XLINK の窓・ディスク・ACIA・電源だけを、レジスタを通す (PSRAM と `settle` は直接のまま)。
* Z80: クロックイネーブル `cen_raw` を 1 クロック前にレジスタに。`cen` から `rd_start` `wr_end` を外す (CLKDIV ≥ 7)。I/O 書き込みの合図 `s_we` をレジスタに。`cen_raw` と `zstall` に `syn_maxfan`。

**やめたこと**: PSRAM のコントローラ (sim09 の外部コード) の CK 出力にレジスタを挟む変更。+0.668 ns まで上がったが、CK のタイミングが変わる (約 0.75 クロック) ので採用しなかった。SD ディスクの戻り先の事前計算は、効果がなかった。

**ROM イメージの置き場所**: LSN 720 から LSN 1100 に移した (15 章)。

### 17.8 6809 の命令ごとの待ちを RTL で測り直す (2026-11-03)

17.4 の係数は、微小ループ (RAM を 1 回読む、など) とそのときの `duo` に合わせた平均で、OS-9 の実際の命令の並びでは ±5% ずれました。そこで、**実際の負荷 (OS-9 で `duo -1`) の全バスサイクルを RTL (Verilator) で記録**し、命令ごとの待ちを表にしました。

**1. サイクルの種類ごとの長さ** (`fpga/tn9k/sim/sim_top.v` に一時的に入れた集計。E のサイクル 36 クロックに対して)

| サイクル | 直前が PSRAM でない | 直前も PSRAM のアクセス |
|---|---|---|
| 命令の先頭の取り出し (RAM) | 48.2 (+12.2) | 51.2 (+15.2) |
| 読み出し (RAM) | 47.3 (+11.3) | 53.2 (+17.2) |
| 書き込み (RAM) | 42.0 (+6.0) | 42.9 (+6.9) |
| アクセスなし (VMA = 0) | 36.0 | 36.0 |
| I/O の読み出し | 46.8 (+10.8) | 48.7 (+12.7) |

前のサイクルも PSRAM のアクセスだと、読み出しが約 5 クロック長くなります (`settle` の 6 クロックが続けて重なる)。これが、17.4 で「RAM にあるコードの命令の取り出しが +31」と説明できなかったものの正体です。

**2. 命令ごとのバスサイクルのパターン** (`fpga/tn9k/test/m6809_patterns.txt`、約 430 行): 命令ごとに、サイクルの並びを文字にしました (`F` 取り出し、`r` 読み出し、`w` 書き込み、`d` アクセスなし、`i` `j` I/O)。例:

| 命令 | パターン |
|---|---|
| `NOP` `COMB` (1 バイト) | `Fr` (2 サイクル目も RAM を読んでいる) |
| `BEQ` `BNE` | `Frd` |
| `LDA ,X+` など (索引) | `Frrdr` |
| `STD` (索引) | `Frrdww` |
| `MUL` | `Frddddddddd` |
| `JSR` | `Frrdrw` ほか |

同じオペコードでもサイクル数 (索引のモードなど) でパターンが変わるので、(オペコード, サイクル数) で引きます (`tools/mkm6809hw.py` が `src/m6809hw.h` を作る)。表に無いものは「`F`、1 回読む、残りはアクセスなし」とします。

**3. シミュレータ** (`machine.c` の `hw_settle`): 命令ごとに、次の命令のオペコードの取り出しの時点で、前の命令を (オペコード, 実際のサイクル数) でパターンに当て、1 の表で待ちを足す。直前のサイクルが PSRAM かどうかは命令をまたいで持ち越す。PSRAM のアクセス 1 回ごとに、Z80 との競合を調べる。ROM にあるコード (Level 1 の試験プログラム) は、アクセス 1 回ごとの旧モデル (読み出し +10.4、書き込み +5.4) のまま。

**4. 結果** (`duo`、PSRAM の占有時間は両方の CPU の時間が合うように 9 クロックに決め直した。24 → 9):

| | シミュレータ | 実機 | 差 | 17.7 の差 |
|---|---|---|---|---|
| `-1` (6809 だけ) | 7.61 s | 7.75 s | −1.8% | −4.8% |
| `-z` (Z80 だけ) | 18.24 s | 18.08 s | +0.9% | +2.1% |
| 二つ | 5.63 s | 5.78 s | −2.7% | +1.2% |

最大の差は 4.8% から 2.7% になりました。残る差の原因は、割り込みの入り方 (スタックへの退避の並び) と、表に無い命令、ACIA の送信待ちなどを入れていないことです。
