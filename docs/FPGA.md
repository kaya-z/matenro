# FPGA への実装の検討 (Tang Nano 9K / 20K)

> これは**検討書**です。RTL は XLINK と、Z80 をつないだ `z80_soc.v` (シミュレーションのみ、メモリは配列) までです。数字は 3 種類あり、本文では区別して書きます:
> **[実測]** 既存の sim09 の FPGA 版 (`new-sbc09/fpga/tn9k/build/fuzix_nohdmi`) の合成・配置配線のレポートから読んだ値、
> **[資料]** デバイスのデータシートなど公開資料の値 (手元の Gowin IDE には容量の表がなく、確認していません)、
> **[見積]** 一般的な傾向からの推定 (**測っていません**。オープンな Z80 / 8086 のコアのソースが手元にないため)。
> HDMI は検討の対象外です (指示どおり)。

## 1. 結論

| 構成 | LUT4 (見積) | 判定 |
|---|---|---|
| **Tang Nano 9K** (8,640 LUT4) + 6809 + **Z80**、HDMI なし | 約 7,200-7,400 (84-86%) | **入る見込み** (コアと XLINK は実測、調停だけ見積もり)。LUT は 1 割強の余裕。ただし 67.5MHz の配置配線 (Fmax が 72-76MHz、CLS は現行で 76%) が通るかは、つないで配置配線するまで分からない |
| Tang Nano 9K + 6809 + **8088** | 約 8,800-12,000 (100% 超が普通) | **入らない見込み** (6809 コアだけで 3,281 LUT4 [実測]) |
| Tang Nano 9K + HDMI (sim09 の FPGA 版は HDMI + 漢字で LUT 86% [`new-sbc09/docs/FPGA.md`]) + サブ CPU | 9,400 以上 | 入らない |
| **Tang Nano 20K** (20,736 LUT4 [資料]) + 6809 + Z80 または 8088 (HDMI あり/なし) | 約 9,400-14,100 (45-68%) | **余裕で入る**。両方のサブ CPU を同時に載せて切り替えることもできる |

**推奨**: まず 9K で「6809 + Z80 + XLINK」を試し (入れば最小構成)、8088 が必要な場合、または 9K の配置配線が通らない場合は 20K に移ります。

## 2. 手がかり: sim09 の 9K 版の実測 [実測]

`fpga/tn9k/build/fuzix_nohdmi` (HDMI なし、Level 2 の MMU を含む) の合成レポートの階層別の資源:

| モジュール | LUT4 (ALU を除く) | ALU | レジスタ | BSRAM |
|---|---|---|---|---|
| `cpu` (Greg Miller の MC6809 コア `mc6809i.v`) | **3,281** | 119 | 204 | 0 |
| `soc` (バス、MMU、ROM、レジスタの束) | 776 | 44 | 401 | 1 |
| `disk` (`sd_disk.v`: SPI の SD カードと DMA) | 469 | 62 | 311 | 1 |
| `timer` (`timer_rtc.v`) | 252 | 17 | 151 | 0 |
| `loader` (漢字データのローダ) | 176 | 0 | 126 | 0 |
| `acia` (UART) | 100 | 15 | 103 | 1 |
| `psram` (PSRAM コントローラ) | 77 | 14 | 104 | 0 |
| `arb` (PSRAM の調停) | 12 | 0 | 52 | 0 |
| `top` | 9 | 15 | 20 | 0 |
| **合計 (配置配線後)** | **5,142** | **316** | **1,472** | **3** |
| デバイスの総数 | 8,640 (LUT + ALU) | | 6,771 | 26 |
| 使用率 | **64%** (LUT + ALU = 5,458) | | 22% | 12% |

(これは sim09 の SoC です。Z80 と XLINK を足した今の使用量は、モジュール別の表も含めて [FPGA_RESOURCES.md](FPGA_RESOURCES.md) にあります。)

* CLS (論理スライス) の使用率は 76% (3,272 / 4,320)。配置配線は LUT の使用率が 8-9 割を超えると急に難しくなります。
* RAM 64KB は BSRAM (26 ブロック = 468Kbit で足りない) ではなく、パッケージ内の **PSRAM (64Mbit = 8MB)** に置いています。
* クロックは水晶 27MHz から PLL で **67.5MHz**、6809 の E は ÷36 で **1.875MHz**。PSRAM の読み出しが E の半周期に収まらないときは E を止めて
  待ちます (実効は約 1.54MHz)。PSRAM が安定して動く範囲は 54-74.25MHz (81MHz は誤り)、論理の Fmax は 72-76MHz です。
* ここに無かったもの: 漢字のローダを外すと −176、タイマを小さくすれば −100 程度は削れそうです。

## 3. サブ CPU のコアと XLINK の大きさ [実測 / 見積]

Z80 コアと XLINK は Gowin IDE で**合成して測った値** (配置配線はしていない)、8088 コアと調停は**測っていない見積もり**です。

| 部品 | LUT4 の目安 | 備考 |
|---|---|---|
| **Z80 コア [実測]** (TV80 `tv80s`、Mode 0 = Z80。hutch31/tv80、MIT) | **1,392 + ALU 54 = 1,446**、レジスタ 230、SSRAM 12 | 合成だけ。9K と 20K で同じ値。内訳: コア本体 1,122、マイクロコード `i_mcode` 224、ALU 8、レジスタファイル 6 (+SSRAM 12)、ラッパ 32。8MHz のタイミングは配置配線をしていないので未確認 |
| 8088 / 8086 コア (MCL86、Zet86 系) | 3,000-6,000 | マイクロコード ROM に BSRAM を 1-4 ブロック使うものが多い。バイト幅バスの 8088 版が望ましい |
| **XLINK + SMMU [実測]** (`fpga/rtl/xlink.v`: レジスタ、メールボックス、ドアベル、128 × 8 ビットの SMMU、ウィンドウのカウンタ、32 ビットのクロックカウンタ) | **377 + ALU 31 = 408**、レジスタ 201、BSRAM 1、SSRAM 16 | 9K (`GW1NR-9C`) と 20K (`GW2AR-18C`) で同じ値。合成だけ (配置配線はしていない)。読み出しポートが 2 つ (サブ CPU のアドレス変換と 6809 の読み出し) あるので表が BSRAM と SSRAM に二重に写っている |
| メモリ調停を 2 マスタに拡張 | 100-300 | 6809 側とサブ CPU 側、ウィンドウ DMA の 3 マスタになる |

合計の追加は **Z80 構成で約 1,950-2,150** (1,446 + 408 [実測] + 調停 100-300 [見積])、**8088 構成で 3,500-6,700** くらいです (コア 3,000-6,000 [見積] + 408 + 調停)。
1 章の表はここから出しました: 9K は 5,458 − 176 (漢字ローダを外す) + 追加分、20K の HDMI 付きは 7,430 (86% × 8,640) + 追加分です。

## 4. 9K で足りない理由と、20K を使う場合

| | Tang Nano 9K [資料] | Tang Nano 20K [資料] |
|---|---|---|
| FPGA | GW1NR-9 | GW2AR-18 |
| LUT4 | 8,640 | 20,736 |
| レジスタ | 6,480 (+ I/O 291) | 15,552 |
| BSRAM (18Kbit) | 26 (468Kbit) | 46 (828Kbit) |
| 外付けに見えるメモリ | PSRAM 64Mbit (8MB、パッケージ内、HyperRAM 系の 8 ビット DDR) | SDRAM 64Mbit (8MB、パッケージ内、16 ビット) |
| クロック | 27MHz 水晶 | 27MHz 水晶 |
| SD カード | microSD スロット | microSD スロット (ピン割り当ては作り直し) |
| HDMI | 付いている (今回は不要) | 付いている |

* 手元の Gowin IDE (`/usr/local/IDE`) は両方のデバイス (`GW1NR-9C`、`GW2AR-18C`) に対応しています (`share/device/` を確認)。
  20K のボードのピン割り当て (`.cst`) と、SDRAM のコントローラ (PSRAM のものは使えません) は**新しく用意する**必要があります。これが 20K の
  主な追加作業です。
* 20K では LUT に余裕があるので、6809 + Z80 + 8088 を**全部載せて、`XID` で選ぶ** (または `XC` のレジスタで切り替える) こともできます。
  シミュレータの `sub_cpu_ops_t` に対応して、RTL でも CPU を同じバス (メモリ・I/O・割り込み) に差し込む作りにします。

## 5. メモリ構成の検討 (共有メモリ)

### 5.1 1 ポートの外付け RAM を 2 つの CPU で使うと

PSRAM の読み出しは 67.5MHz で 12-20 クロック (178-296ns) [実測 / FPGA.md の記述]です。各 CPU のバスサイクルとの比:

| CPU | クロック (67.5MHz から作る) | 1 バスサイクル | PSRAM を占める割合 |
|---|---|---|---|
| 6809 | E = 1.875MHz (÷36) | 533ns | 33-56% |
| Z80 | 7.5MHz (÷9) | 3-4 クロック = 400-533ns | 33-74% |
| 8088 | 7.5MHz (÷9) | 4 クロック = 533ns | 33-56% |

6809 とサブ CPU を足すと**ほぼ 100% かそれ以上**になる場面があり、片方 (または両方) にウェイトを入れる調停が必要です。
Z80 は `/WAIT`、8088 は `READY`、6809 は E を止める (現行の方法) で待たせられます。どれだけ遅くなるかは、シミュレータに
**メモリ競合のモデルを入れてから**見積もるのが筋です (DESIGN.md の 17 章: `-hw` で実装済み)。

### 5.2 BSRAM のデュアルポートを共有領域にする (推奨)

**実装済み (2026-11-07): 8KB。** `fpga/rtl/shr_ap.v`: 物理ブロック `SHR_BLK` (既定 `$FF` = `$1FE000`-`$1FFFFF`、8KB) だけを PSRAM ではなく BSRAM (DPB 4 ブロック) から読み書きします。A ポートは Z80 のメモリポート、B ポートは 6809 のウィンドウ (`XE_WA`/`XE_WD`) です。調停回路を通らないので、Z80 は待たされず、6809 のウィンドウも 2 クロック台で終わります。使い方は SMMU の物理ブロック番号に `$FF` を入れるだけで、ソフトウェアは変わりません (例: `XE_MI` = 0、`XE_MD` = `$FF` で Z80 の `$0000`-`$1FFF` が BSRAM になる)。
* **6809 の MMU 経由の直接共有 (`XC_SHR`) では見えません**。ブロック `$FF` を 6809 の MMU に写すと PSRAM の同じ番号が見えるので、ウィンドウで触ってください。OS-9 の `xlink` ドライバが 2MB のプールの最後のブロックを割り当てる場合も、Z80 とウィンドウからは BSRAM、6809 の MMU からは PSRAM になります。
* 同じバイトを 2 つの CPU が同じクロックで書いたときの結果は決まりません (ドアベルで順序を付ける使い方なら問題ありません)。
* 資源 (配置配線後): Logic 7,729 / 8,640 (90%、+63)、CLS 4,070 / 4,320 (95%)、BSRAM 8 / 26 (+4)。**Fmax 68.0MHz (制約 67.5MHz)、負のスラックなし**。最初の配置配線は 63.8MHz で通らなかった。遅い経路は追加した回路ではなく、SMMU の読み出し (BSRAM の出力は clock-to-out が 3.5ns) だったので、`xlink.v` の `smmu_rd` の後ろに FF を 1 段足した (6809 が SMMU を読むのは索引を書いてから 18 クロック以上あとなので、影響はない)。Gowin の DPB は read-before-write が使えないので、書き込みのときは write-through (書いたデータを読み出しに出す) にした。
* 試験: `make -C fpga/sim soc` の 21 項目 (BSRAM にイメージを書いて読み戻す、Z80 を BSRAM から動かして 5050 と 55、PSRAM 側のブロックに触れていない) に加え、実機では `fpga/tn9k/test/xlshr.asm` (`XLASM=xlshr TAG=_shr scripts/build.sh xltest`) が、Z80 のブロック 0 を BSRAM に写して `13BA` `0037` を得て、ウィンドウで BSRAM の結果 (`3700`) を読み戻した。通常の起動 (`boot`) では OS-9 が起動し、`duo` が 5.8 秒で動いた。
* 広げるには: 16KB (BSRAM 8 ブロック) は SMMU の 2 ブロック分で、出力の選択論理が増えます。CLS が 95% なので、配置配線の結果次第です。

(以下は設計時の検討)

Gowin の BSRAM は**真のデュアルポート**にできます。2 つの CPU が**同じ BSRAM を別々のポートから**読み書きすれば、調停も待ちもありません。

* 9K: 26 ブロックのうち現行で 3 つを使っていて、残り 23 ブロック = 約 46KB (8 ビット幅で 1 ブロック 2KB)。
  共有領域 16-32KB (メールボックスや受け渡しのバッファ、Z80 の速いワーク RAM) を BSRAM に置き、大きな領域 (OS-9 の RAM、Z80 の 64KB の残り)
  は PSRAM、という二層にします。
* 20K: 46 ブロック = 約 92KB。共有領域を大きく取れ、SDRAM の遅さを避けられます。
* 現行のシミュレータの SMMU (8KB ブロック単位の物理アドレス) はそのまま使えます: 物理アドレスの特定の範囲を「BSRAM」に割り当てるだけです。

### 5.3 Z80 の 64KB の置き方

Z80 の全空間 (64KB) を BSRAM に置くと 9K では 32 ブロック必要で入りません。PSRAM を使い、頻繁に使う 16-32KB (スタック、ワーク、
ISR) を BSRAM に写すか、キャッシュ (1 ライン 16 バイトなど) を置く、という選択になります。最初の版は「全部 PSRAM + 調停」で十分で、
BSRAM の共有領域は後から足せます。

## 6. クロック

* **9K, 現行の 67.5MHz (推奨)**: 6809 の E は 1.875MHz (最大 2MHz の 94%)、サブ CPU は ÷9 で **7.5MHz** (最大 8MHz の 94%)。
  実績のある PLL の設定がそのまま使えます。
* **9K, 72MHz** (27MHz × 8 ÷ 3、VCO 576MHz): E = 72/36 = **2.0MHz**、サブ CPU = 72/9 = **8.0MHz** と、**ちょうど最大クロック**になります。
  ただし PSRAM が検証された範囲 (54-74.25MHz) の端で、論理の Fmax (72-76MHz) とも重なるので、**タイミングが通るか分かりません**。
  64MHz は PFD が 1MHz になって PLL の下限 (3MHz) を割るので使えません。
* (現行の実装のクロックの系統は **9.9 節の系統図** にあります。)
* 20K: SDRAM 用に別の PLL を使い、CPU 側は同じく 1 つのシステムクロックの**クロックイネーブル**で作ります (同期設計。
  CPU 間の信号は同じクロックドメインなので、メールボックスの同期回路が要りません)。

## 7. ストレージ (SD カード)

* 6809 側のディスクは既存の `sd_disk.v` をそのまま使います (SPI モード、初期化 263kHz → 通常 11.25MHz、カードの 512 バイトのブロックを
  256 バイトのセクタの DMA で PSRAM とやり取り)。OS-9 の RBF ドライバは変わりません。シミュレータの「ディスクイメージ = SD カードの生デバイス」
  という扱いと同じです。
* サブ CPU は SD カードに**直接触りません**。XLINK のメールボックスで 6809 (OS-9) に頼みます。FPGA でも同じです。
* 20K では SD カードのピンが違うので `.cst` を作り直し、同じ SPI モードで使います (ピンは実機で合っていた: TN20K.md の 8 章)。

## 8. 進め方 (提案)

1. **XLINK の RTL** — **書きました** (`fpga/rtl/xlink.v`)。Verilator のテスト (`make -C fpga/sim`、43 項目: レジスタ、メールボックス、ドアベルと割り込み、SMMU、ウィンドウ、クロックカウンタ) は通り、Gowin で合成して 408 LUT を実測しました (`fpga/synth/run.sh 9k xlink fpga/rtl/xlink.v`)。
   **Z80 側は済み**: `fpga/rtl/z80_soc.v` (TV80 + XLINK + SMMU + RAM) で `os9/sub/sumz80.py` (C のシミュレータと**同じバイナリ**) を動かし、1+…+100 = 5050、1+…+10 = 55 が C と同じにメールボックスと共有 RAM に出ることを確認しました (`make -C fpga/sim soc TV80=…`、11 項目。テストベンチが 6809 の役で XLINK のレジスタを叩き、`xrun` と同じ手順: ウィンドウで読み込み → 起動 → ready → n を送る → doorbell → 返事)。
   **まだ**: `tests/mh/xlink_test.asm` と 8088 側、実際の 6809 コアとの接続。
2. **Z80 のコア** — TV80 を単体で合成して **LUT 数を実測しました** (`fpga/synth/run.sh 9k tv80s ...`、3 章)。
   **つないだ分**: Z80 (TV80 `tv80s`) のバス (メモリ、I/O ポート `$00-$0F`、割り込み応答 = M1+IORQ、NMI、HALT、バス要求) を XLINK につなぎ、メモリを SMMU 経由で物理 RAM に出す部分を `z80_soc.v` に書きました。合成したロジックは Z80 + XLINK + つなぎで **約 1,610 LUT + ALU 54** です (コア 1,043 + 238 + 8 + 7、XLINK 284、つなぎ 30; `fpga/synth/z80_soc_syn.v`、RAM を 1KB にして測定、配置配線なし)。
   **分周も済み**: Z80 は `clk / CLKDIV` のクロックイネーブル (67.5MHz ÷ 9 = 7.5MHz) で動きます。TV80 の `tv80s` は `cen` を 1 に固定しているので、`fpga/sim/mk_tv80s_cen.sh` が sed で `cen_i` ポートつきの `tv80s_cen` を作ります (TV80 のファイルはリポジトリに入れず、手元のものから作る)。CLKDIV = 2, 3, 4, 9, 12 で同じ 11 項目が通ります (1 は未対応)。遅いクロックのために、(1) NMI のパルスを次の `cen` まで保持、(2) コアが T2 のあいだずっと `di` を取り込むので、データバスの選択をサイクルの頭で決めて次のサイクルまで保持、(3) I/O の書き込みはサイクルの終わり (WR が上がるとき) に、最後のクロックのデータとポートで行う、を入れました。合成は CLKDIV = 9 で約 1,620 LUT (つなぎ 38、XLINK 288、コア 1,296 ほか)。
   **まだ**: sim09 の SoC (`new-sbc09/fpga/tn9k/rtl/sbc09_soc.v`) への接続、PSRAM の調停とウェイト、配置配線でのタイミング確認。
3. 9K で入らない / 通らなければ 20K へ。SDRAM コントローラとピンを用意し、8088 のコアを載せる。
4. 調停にウェイトを入れ、BSRAM の共有領域を足して、シミュレータの競合モデル (`-hw`、実装済み) と比べる。

**確認できていないこと**: 3 章の 8088 コアの LUT 数 (測っていません。コアのソースが手元にありません)、調停の LUT 数、Z80 を載せた 9K の配置配線とタイミング、20K のボードの SDRAM・SD・HDMI のピンと速度、72MHz でのタイミング、
候補のコアのライセンスと実際の動作。

## 9. sim09 の SoC への統合 (6809 コア + PSRAM + SD + Z80) — 実機 (Tang Nano 9K) で確認済み

`fpga/tn9k/` に、sim09 の Tang Nano 9K 版 SoC (`new-sbc09/fpga/tn9k`) に Z80 を足したものがあります。sim09 のファイルは**読み取り専用で参照**し (UART、タイマ、SD ディスク、PSRAM コントローラ、6809 コア、PLL、ピンとタイミングの制約)、変えたものだけを複製しました (`CREDITS.md`)。

| ファイル | 内容 |
|---|---|
| `rtl/matenro_soc.v` | `sbc09_soc.v` に XLINK ( I/O ページの `$4A-$4E` = Level 2 の `$FFCA-$FFCE`、Level 1 の `$E04A-$E04E`)、Z80 (`z80_sub.v`)、ウィンドウ、IRQ の OR を足したもの |
| `rtl/psram_arb4.v` | PSRAM の調停に、4 番目のマスタ (Z80、バイトの読み書き) と 5 番目のマスタ (ディスクの非同期モードの DMA、最低優先) を足したもの。優先順位は HDMI の 2 つ > Z80 > 6809 (起動時の消去、XLINK のウィンドウ、同期モードのディスク) > 非同期のディスク |
| `rtl/tn9k_top.v` | `matenro_soc` を使う最上位 (`MEMTEST` を 0 にして面積を減らす) |
| `../rtl/z80_sub.v` | Z80 + XLINK + クロックイネーブルの分周。メモリは要求/応答のポート (何クロックかかってもよい) |
| `constraints/matenro.sdc` | Z80 のためのマルチサイクルのタイミング制約 |
| `test/xltest.asm` | 6809 のテスト用 ROM: `xrun` の役 (ウィンドウで Z80 のデモを読み込む → 起動 → n = 100, 10 を送る → 返事を UART に出す) |
| `sim/` | Verilator のテスト。sim09 の `tb.cpp` と PSRAM のモデルを使う (`make -C fpga/tn9k/sim TV80=…`) |
| `scripts/build.sh` | Gowin の `gw_sh` でビットストリームを作る (`TV80=… fpga/tn9k/scripts/build.sh xltest`) |

**シミュレーション**: 6809 の RTL コア (Greg Miller)、PSRAM のモデル、XLINK、TV80 の Z80 を全部つないで、`xltest` が UART に `13BA` と `0037` を出しました (C のシミュレータと同じ値。`sumz80` を使い、6809 から Z80 へのウィンドウ読み込み、起動、ドアベル、割り込み、返事、Z80 の PSRAM アクセスまで通っています)。

**合成と配置配線 (`GW1NR-9C`)**: LUT/ALU 7,771 / 8,640 (**90%**)、CLS 94%、レジスタ 32%、BSRAM 4 / 26。**67.5MHz の制約で、Fmax 68.1MHz、セットアップとホールドの負のスラックなし** ( `matenro_xltest.fs` ができる)。最初の配置配線は Fmax 26.7MHz で、次の変更で届きました。

* Z80 のコアのレジスタは、クロックイネーブル (9 クロックに 1 回) のときだけ変わるので、コアの中の経路は 9 クロックある。Gowin のタイミング解析には**マルチサイクルの制約**で教える必要があります (`set_multicycle_path -from … -to … -setup -end 9`)。ツールは `-from` と `-to` の両方がないと効かず、RAM セル (SSRAM の`RegsH`/`RegsL` 12 個) は `get_regs` では見つからず、ピン (`DI[n]`, `WAD[n]`, `AD[n]`, `WRE`) を 1 つずつ書き、リストは約 4000 文字までです。存在しないピンを書くとツールは**エラーで止まって古いビットストリームが残る**ので、`build.sh` はエラーを見つけたら失敗にします。
* 読み出したデータの経路を短くするため、バスのラッパ (`tv80s_cen`: RD, WR, MREQ, IORQ とデータのラッチ) はクロックイネーブルの 4 クロック後にだけ値を取り (`upd_i`)、`di` は 1 クロック遅らせた `di_q` を使い、メモリのアクセスが終わってから 5 クロックはクロックイネーブルを止め (`zrel`)、XLINK のレジスタ読み出しは 1 クロック遅れで返します (`m_rdata`)。
* これらは**タイミング解析に教えた仮定**です。実機で確かめるまでは、仮定が正しいという保証にはなりません。仮定が守られているかは、シミュレーション (クロックイネーブルの分周比を 2〜12、メモリの遅れを 0〜30 クロックにして同じ結果) で確かめました。レジスタの読み出し中に Z80 が同じレジスタを書き換えると、古い値と新しい値のビットが混ざった値が見える可能性があります (本物の Z80 システムでも起こる競合です)。
* Z80 のクロックイネーブルの分周比 (`CZ_DIV`) は 9 で、制約はこの値を前提にしています。変えたら `constraints/matenro.sdc` の数 (9, 5, 4, 3) と `UPD` を見直してください。

**実機での確認 (済み)**: `matenro_xltest.fs` を `openFPGALoader -b tangnano9k` で SRAM に書き込み (フラッシュは書き換えない)、USB のシリアル (FT2232 の 2 つ目のポート、115200 baud) に `SLR13BA` `0037` が出ました (GW1N-9C、IDCODE `0x100481b`)。長時間の連続動作と温度による変化は見ていません。`SLR` の `S` は起動、`L` は Z80 のプログラムの読み込み完了、`R` は Z80 の ready を受けた印です。これで OS-9 Level 2 を載せるには、SD カードのイメージ (sim09 の Level 2 ローダ) とドライバ `xlink` を使います ( `-m 1M` は要りません)。

### 9.1 OS-9 Level 2 を SoC で起動する (RTL シミュレーションと実機 Tang Nano 9K で確認済み)

sim09 の 256 バイトの起動 ROM (`$FF00`) が SD カードの LSN 2 から Level 2 のローダを読み、ローダが Level 2 の ROM イメージを PSRAM に置いて起動します (`new-sbc09/tools/mkl2disk.py`)。この SoC は同じ ROM で動きます。

* **SD イメージ**: `fpga/tn9k/scripts/mkdisk.sh OUT.dsk` が sim09 の `os9/OS9L2.dsk` に Matenro のコマンド (`cpm xrun xlink x0 cpp80 cc80`) と `hello.com` を入れます (1MB、4096 セクタ、空きは約 1930 セクタ)。カードには `sudo dd if=OUT.dsk of=/dev/sdX bs=512 conv=fsync` で書きます (**カード全体が上書きされる**ので、デバイス名を確かめてください。ここでは書いていません)。
* **ビットストリーム**: `TV80=… fpga/tn9k/scripts/build.sh boot` (起動 ROM 版)。LUT 89%、CLS 93%、**Fmax 67.9MHz、負のスラックなし**。
* **RTL シミュレーション**: `make -C fpga/tn9k/sim ROM=boot boot TV80=… DISK=OUT.dsk SCRIPT=… CLKS=4000000000` (2.8 億クロック、SD から 146 ブロックを読んで OS-9 Level 2 が起動)。`load xlink`、`load x0` のあと **`cpm /d0/hello.com abc` が `Hello from CP/M-80 on the Z80` と ` ABC` を出しました** (6809 の RTL コア、PSRAM のモデル、SD のモデル、XLINK、TV80 の Z80、ドライバ `xlink` が OS-9 の空き RAM から借りた Z80 のメモリ)。
* **実機 (Tang Nano 9K)**: ビットストリーム `matenro_boot.fs` をフラッシュに書き (`openFPGALoader -b tangnano9k -f`)、`matenro_l2.dsk` を SD カードに書いて電源を入れると、シリアルに `NitrOS-9/6809 Level 2 V1.0.1` / `Tang Nano 9K` が出て OS-9 が起動し、`chx /d0/cmds`、`load xlink`、`load x0`、`cpm /d0/hello.com abc` で **`Hello from CP/M-80 on the Z80` / `!` / ` ABC`** が出ました (FPGA の 6809 が OS-9 Level 2 を動かし、同じ FPGA の Z80 が CP/M-80 のプログラムを動かし、OS-9 がその BDOS 呼び出しを引き受ける)。
* **タイミングは配置配線の結果で変わります**: 同じ RTL でも変更のたびに Fmax が 64〜68MHz の間で動き、67.5MHz に届かないことがあります (`xltest` を作り直したときは Fmax 64.7MHz、スラック -3.4ns で、実機では動きましたが制約は満たしていません。`PLACE=1..4` の配置オプションは同じ結果でした)。ビットストリームを作ったら必ず `impl/pnr/*_tr_content.html` の `Total Negative Slack Summary` を見てください。`MEMTEST=0` で消えるメモリ試験の回路を `MEMTEST` で守ったのは、この余裕を作るためです。

### 9.2 SD カードのイメージ (ドライブ 0 と 1)

カードは生のまま、ドライブ 0 = バイト 0 から、ドライブ 1 = 128MB の位置から (`sd_disk.v` の `DRIVE1_BLK`、LSN *n* = バイト *n* × 256) です。

| ファイル (`fpga/tn9k/build/`、git には入れない) | 内容 |
|---|---|
| `matenro_l2.dsk` (1MB、4096 セクタ) | `/d0`: OS-9 Level 2 のローダと ROM イメージ、コマンド、Matenro のコマンド (`cpm xrun xlink x0 cpp80 cc80`)、`hello.com` (`scripts/mkdisk.sh`) |
| `matenro_d1.dsk` (512KB、2048 セクタ。**`matenro_d1_big.dsk` は 64MB**、下) | `/d1`: **HI-TECH C** (`/d1/htc`: P1 CGEN ZAS LINQ、`CRTCPM.OBJ`、`LIBC.LIB` `LIBF.LIB`、ヘッダ)、**`zexdoc.com` `zexall.com`**、`zexdoc8.com` `zexall8.com` (8 項目目だけ)、`bstress.com` (リンクの負荷試験)、`demo.c` `mandel.c` `hello.c` (`scripts/mkdisk_d1.sh`)。**空きは 130 セクタ** (Turbo Pascal を入れたあとの実測。以前の 475 は古い)。`cc80 -r` はできた `.COM` を残すので、`hello.c` と `demo.c` を動かすだけで 20 セクタほどまで減り、`mandel.c` のコンパイルが入らなくなる。使い終えたら `del` で消す。2048 セクタは 1 セクタの割り当て表で持てる最大 |
| `matenro_card.img` (約 128MB) | 上の 2 つを置くべき位置に置いたカード全体のイメージ: `sudo dd if=matenro_card.img of=/dev/sdX bs=1M conv=fsync` (**カード全体が上書きされる**。128MB 以上のカード) |
| `matenro_card_big.img` (約 192MB) | `/d0` と 64MB の `/d1` を置いたカード全体 (`fpga/tn9k/scripts/bigd1.sh`)。192MB 以上のカードに書く |

実機での使い方 (実機で確認済み。`cc80 -t=/d1/htc -r hello.c` と `mandel.c`、`cpm zexdoc`): `chx /d0/cmds`、`load xlink`、`load x0`、`chd /d1`、`cc80 -t=/d1/htc -r hello.c` (HI-TECH C)、`cpm zexdoc` (ZEXDOC)。`cc80 -t=/d1/htc -r hello.c` はシミュレータ (`/d1` を 2 番目のディスクイメージにしたもの) で `Hello from Hi-Tech C on CP/M` まで通りました。

**`/d1` を 64MB のハードディスクにする (2026-11-07)**: `/d1` は 2048 セクタ (512KB) で、空きが 130 セクタしかなかった。2048 セクタは `sim09` の `growdisk.py` と `mkdisk_d1.sh` が 1 セクタの割り当て表に決めていた大きさで、OS-9 の RBF の限界ではない (`rbf.asm` の `FatScan` は `DD.MAP` バイトの表を、複数のセクタにまたがって調べる。`DD.MAP` の上位バイトが表のセクタ数なので、255 セクタ = 約 52 万クラスタまで)。カードは (以前の `dmesg` で) 約 3.75GB で、ドライブ 1 は 128MB の位置から始まるので、広げるのに場所の制約はない。SD カードの RTL (`sd_disk.v`)、OS-9 のドライバ、デスクリプタ、シミュレータは**変えていない** (ドライブ 1 のままで、LSN の大きさが違うだけ)。

**実機の結果 (2026-11-07)**: `matenro_card_big.img` を SD カードに書いて確認した。`free /d1` は 262,144 セクタ (1 セクタクラスタ)、空き 260,113 セクタ。`chd /d1` のあと `cc80 -t=/d1/htc -r` で `hello.c` `demo.c` `mandel.c` をコンパイルして実行でき、`.COM` を残しても空きは 260,000 セクタ台のままだった (`hello.c` と `demo.c` で 55 セクタ程度)。

* `tools/mkrbf.py`: 空の RBF ボリュームを作る (既定 262144 セクタ = 64MB、1 セクタ/クラスタ、割り当て表 128 セクタ)。LSN 0、表 (LSN 1〜)、ルートディレクトリの FD、ルートディレクトリを書く。
* `fpga/tn9k/scripts/bigd1.sh OLD NEW`: 古い `/d1` のファイル (属性も) を、シミュレータの `copy` で新しい大きなボリュームに移す (2 台のドライブしかないので、ホストのディレクトリ `/v0` を通す)。`CARD=` でカード全体のイメージも作る。`tools/rbfwalk.py` が古いイメージのファイルの一覧を作る。
* 確認: 61 件 (ファイル 57、ディレクトリ 4) の中身 (MD5) と属性が古い `/d1` と同じ。1MB のファイル 3 つを表の 2 セクタ目以降 (LSN 3000h、4800h) まで書いて、読み戻した内容が同じ、消すと空きが元に戻る (`tests/matenro_test.py` の `os9_bigdisk`)。`hello.c` `demo.c` `mandel.c` を続けて `cc80` で動かしても足りる (空き 259,943 セクタ)。
* `dcheck` は、`sim09` の元のボリューム (`/d0`、古い `/d1`) でも大量の「Cluster … in allocation map but not in file structure」を出す。新しいボリュームでは 1 件「Segment out of range」が出るが、`file structure is intact` で、読み書きと空きの計算は正しい。`dcheck` は検査の基準にしていない。
* 最初の割り当てが大きなファイルだと、1 回だけ `Media Full` (エラー 248) で失敗し、次は通る。`sim09` の元のボリューム (2048 セクタ) でも同じなので、新しいボリュームの問題ではない。
* 実機のカードに書くには、`matenro_card_big.img` (約 192MB) を、192MB 以上のカードに `dd` で書く (カード全体が上書きされる)。

**ファイルの属性 `s` に注意**: OS-9 の `s` 属性 (単一ユーザ = 同時に 1 回しか開けない) が付いたファイルは、HI-TECH のリンカのように**同じファイルを 2 回開く**プログラムでは、2 回目が `E$Share` (`$FD`) で失敗し、リンカは `Can't open` を出します (`/v0` のホストディレクトリでは起きず、RBF のディスクでだけ起きる)。`mkdisk_d1.sh` はコピーのあとに `attr -s` で外します。`cpm -d` は、失敗した `open` の OS-9 のエラー番号を 16 進で表示します。

### 9.3 実機での ZEXDOC と、止まったときの診断 (2026-10-31)

**実機の ZEXDOC** (`cpm zexdoc`、Z80 7.5MHz): 05:18:29 に開始し、7 項目 (`adc,sbc hl` `add hl` `add ix` `add iy` `aluop a,nn` `aluop a,<b,c,...>` `aluop a,<ixh,...>`) が **OK** (誤りの行なし) になりました。所要時間は 9 分、4.5 分、4.5 分、4.5 分、2.3 分、**1 時間 19 分**、40 分で、7 項目目の OK が 07:42:17 です。**8 項目目 `aluop a,(<ix,iy>+1)` の名前が出ないまま 3 時間以上出力がなくなりました** (シミュレータ `matenro` では 67 項目が通り、8 項目目だけを実行する `zexdoc8.com` も 18 秒で OK)。USB の切断ではありません (ログは時刻つきで取っています。01:19 の切断は別件で、そのときのリセットで途中経過を失いました)。

**ここまでに分かったこと** (原因はまだ特定していません):

* シミュレータ (C) では再現しません。RTL (Verilator) で Z80 の計算と BDOS 呼び出しを交互に 3000 回繰り返す負荷試験 `tests/cpm/bstress.asm` は通りました (`bstress.com`)。
* `Ctrl-C` `Ctrl-E` は**停止の判断に使えません**: この OS-9 は端末の入力をプロセスが読むときにしか見ないので、`cpm` を待っている間は効きません (止まった状態でも効かない)。
* **診断ビルド**: `WDOG=1 TAG=_wd TV80=… fpga/tn9k/scripts/build.sh boot` (出力は `build/boot_wd/`)。6809 が約 1 秒以上止まる (stall) と、UART に 31ms ごとに 1 行 (`dbg_uart_z.v`) が出ます。ホストから **`0x1F` を 3 回送ると同じ行をいつでも出し、`0x1E` を 3 回送ると戻ります** (6809 が止まっていても効きます。コンソールの出力は止まります)。行: `PPPP SSSS AA BB XXXX YYYY UUUU CC DD ssss pppp aaaa ff` = 6809 の PC、S、A、B、X、Y、U、CC、DP、`ssss` = CPU を止めているもの (15 `xl_wait`、14 `xl_rcap`、13 `xw_act`、12 `m0_req`、11 `zm_req`、10 `ps_busy`、9 `mem_pend`、8 `acia_pend`、7 `disk_busy`、6 `pwroff`、5 `settle`、4 `stall`、3 `win_req`、2:0 起動の状態)、`pppp` = Z80 の最後の命令フェッチのアドレス、`aaaa` = Z80 のアドレスバス、`ff` = 80 stalled、40 halted、20 `mem_req`、10 `mem_wr`、08 M1、04 MREQ、02 RD、01 WR。
* この診断ビルドは (SMMU の読み出しをレジスタ経由にして) タイミングを満たしています (clk81 67.65MHz、負のスラックなし)。LUT 8,014 (94%) で、**起動 ROM 版 (89%) より約 5% 大きい**ので、普段使いではなく診断用です。ついでに使っていない漢字ローダを外し (`KANJI = 0` のとき)、LUT は 177 減りました。

**2 回目の実行 (診断ビルドで、12:11:12 開始): 67 項目すべて OK、`error` なし、15:15:39 に `Tests complete` (3 時間 4 分)。** 1 回目に止まった場所 (7 項目目の OK のあと) では 8 項目目の名前がすぐ出て、8 項目目は 20 分で OK でした。つまり**1 回目の停止は再現していません**。1 回目と 2 回目の違いは、ビットストリームだけです (1 回目 = フラッシュの起動 ROM 版 `build/boot`、2 回目 = 診断ビルド `build/boot_wd`: SMMU の読み出しのレジスタ、漢字ローダなし、デバッグ UART、別の配置配線)。ランダムな現象か、ビルドの違いかを分けるため、3 回目は 1 回目と同じビットストリーム (`build/boot`) で実行しました。

**3 回目の実行 (起動 ROM 版 `build/boot`、15:34:17 開始): 67 項目すべて OK、`error` なし、18:38:44 に `Tests complete` (3 時間 4 分)。** 7 項目目の OK のあと 8 項目目の名前がすぐ出ました。

**結論 (2026-10-31)**: 実機の Z80 (7.5MHz) は ZEXDOC の 67 項目を**2 回、別々のビットストリームで通しました** (診断ビルドと起動 ROM 版)。1 回目に 7 項目目のあとで出力が止まった件は、**再現せず、原因は分かっていません** (そのときは 6809 側の状態を取れませんでした)。決定的な不具合ではありません (同じ場所で毎回は止まらない)。疑うとすれば、(1) 1 回目の前後にあった USB / 電源の不安定 (01:19 に USB が切れてボードが再起動した)、(2) まれなタイミングの問題 (余裕が 0.1〜0.5ns しかない)、(3) まれな受け渡しの競合、です。次に長い実行をするときは**診断ビルド (`WDOG=1 TAG=_wd`) を使えば**、止まった時点で 6809 と Z80 のどちらがどこにいるかを取れます。

**4 回目の実行 (2026-11-03、タイミングを最適化したビットストリーム `boot_h1`、最悪スラック +0.451 ns): 67 項目すべて OK、`error` なし、20:27 に開始して 23:31 に `Tests complete` (3 時間 4 分)。** 構成は、リセットのあと XLINK ドライバ (`load xlink` `load x0`) を載せ、`cpm` のドアベル待ちが割り込み (`SS.XWait`) の状態。カードは Clock の `D.Poll` を割り込みのときだけにした版、ROM イメージは LSN 1100。1 回目に止まった `aluop a,(<ix,iy>+1)` の手前も、止まらずに通りました (この停止を再現しなかった実行はこれで 3 回目)。


### 9.4 タイミングの余裕を測る (2026-10-31)

Gowin の配置配線ツールは、目標のクロックを満たすと最適化をやめるので、「余裕 0.1〜0.5ns」はそのせいでもあります。そこで同じ RTL (起動 ROM 版) の目標を上げて、ツールが実際にどこまで届くかを調べ (`SDC_SED=… build.sh`)、さらに実機で 74.25MHz に上げて動かしました (`CLK_HZ=74250000 PLL=fpga/tn9k/rtl/tn9k_pll_oc.v`、SRAM に読み込むだけ)。

| 目標クロック | ツールが届いた Fmax | 負のスラック (setup) |
|---|---|---|
| 67.5MHz (今の設定) | 67.7〜67.9MHz | なし |
| 70.2MHz | 60.3MHz | -23.7ns (34 本) |
| 72MHz | 64.8MHz | -35.0ns (58 本) |
| 74.25MHz | 70.7MHz | -5.6ns (12 本) |

ツールのモデル (遅い側の条件) では、67.5MHz のほぼ限界です。**ところが実機は 74.25MHz (+10%) でも動きました**: OS-9 の起動、`cpm hello.com`、`bstress` (3000 回、エラーなし)、`zexdoc8` (8 項目目、18 分 19 秒で OK。67.5MHz では 20 分 08 秒で、クロックに比例)。したがって実チップには、モデルより少なくとも 10% の余裕があります (室温。高温や別の個体では分かりません)。ただし 74.25MHz の試験は数十分で、ZEXDOC の全項目 (3 時間) は 67.5MHz でしか通していません。PSRAM は 81MHz で誤読が出る (sim09 の記録) ので、これ以上は上げられません。

余裕を増やすには、(1) クロックを 54MHz に下げる (+25%。6809 は 1.5MHz、Z80 は 6MHz に落ちる)、(2) 一番長い経路を短くする、のどちらかです。(2) は 9.6 でやりました。

### 9.6 長い経路を短くする、漢字ローダの削除 (2026-11-01)

起動 ROM 版のタイミングレポートで一番余裕のなかった 5 系統の経路を、レジスタを 1 段入れて切りました。動作は変えていません (6809 の側は 1 回の読み書きが 18 クロック以上あくので、1 クロックの遅れは見えません)。

| 経路 (元のスラック) | 直し方 |
|---|---|
| XLINK の索引 `idx` → デコード → メールボックスの書き込み (+0.011ns) | 索引のデコードをフリップフロップに置く (`idx` が変わった 1 クロック後に有効) |
| XLINK の窓アドレス `win_addr` の 21 ビット増分 (+0.061ns) | 7 ビットずつ 3 段の増分にする。桁上げが終わるまで `m_wait` を上げたままにするので、外から見る動きは同じ |

漢字ローダも、コードごと削除しました (`KANJI` パラメータ、フラッシュの SPI、`kanji_ok`、`C_LOAD` の状態、`kanji_loader.v` の読み込み)。もう合成には入っていませんでしたが、設定とポートが残っていました。ボードのフラッシュのピンは、共有の制約ファイル (sim09) が参照しているので、使わない固定値で残しています。`sim_top.v` の `fl_*` `kanji_ok` も、sim09 の `tb.cpp` が使うので残しました。

結果 (`TAG=_opt`、67.5MHz、setup の負のスラックなし):

### 9.7 XLINK の読み出しの不具合と、マイクロ秒カウンタ (実機で確認、2026-11-02)

OS-9 の `etime` (6 章) のために、XLINK にマイクロ秒のカウンタ `XE_US` (拡張レジスタ `$14`〜`$17`) を足しました (`xlink.v`。システムクロックを位相累積で割って正確に 1 µs を数える。クロックは `CLK_KHZ` パラメータ)。
**(2026-11-03 に作り直し)**: 加算と比較と引き算が一つの経路に重なって余裕が +0.04 ns になったので、2 µs 単位のカウンタ (`WRAP = 2*CLK_KHZ/1000` クロック。67.5 MHz で 135) と「後半の 1 µs」のフラグに変えました。ループの中に加算器も比較器もなく、定数との一致だけです (`CLK_KHZ` は 500 の倍数であること)。
実機で `XE_KHZ` (正しくは 7500) が 19484 になって見つかった**不具合**があります: SoC は XLINK を読むたびに、約 5 クロック後にもう一度 `rd_reg` を読み直していました (窓 `XE_WD` の読み出しが遅れて届くため)。
しかし**索引の自動加算** (`XIDX` の bit 7) で通常のレジスタを読むと、読み直す時点で索引が次のレジスタに進んでいて、**次のレジスタの値**で上書きしていました。窓の読み出しは自動加算しないので、今までは問題が出ませんでした。
直し方: 窓が選ばれているときだけ (`xlink.v` の新しい出力 `m_win`) 読み直す。通常のレジスタは、読んだその場の値が正しいので読み直さない。
試験: `fpga/tn9k/test/xltest.asm` が `XE_KHZ` を自動加算で読んで `1D4C` を出す (直す前は `4C00` で失敗する)。C のシミュレータでは起きません。実機の `etime` の時間は、ホストの時計と合いました (`bstress` で 22.05 秒 / ホストで 22.9 秒)。

### 9.9 クロックの系統図 (2026-11-03)

水晶は 27 MHz の 1 つで、PLL が作る **67.5 MHz (`clk81`) の 1 つのクロックにすべての論理が同期**しています。6809 の E / Q、Z80 のクロック、タイマ、UART、SD の SPI は、すべて `clk81` から作ったクロックイネーブルや分周で、別のクロックドメインはありません (例外は PSRAM の CK を出す `clk81p` だけ)。

```
 27 MHz 水晶 (sys_clk, 基板)
     |
     v
 rPLL (tn9k_pll.v)   27 MHz / IDIV 2 x FBDIV 5 = 67.5 MHz = VCO 540 MHz / ODIV 8
     |
     +--> clk81  67.5 MHz  (周期 14.815 ns)  -------- すべての論理 (SoC、XLINK、Z80、UART、SD、タイマ ...)
     |         |
     |         +-- 位相カウンタ div (0..8) と ph (0..3)         [matenro_soc.v]
     |         |     1 位相 = PH_DIV = 9 クロック、1 サイクル = 4 位相 = 36 クロック
     |         |     E  = 67.5 MHz / 36 = 1.875 MHz  (E は ph 0->1 で下がり、ph 2->3 で上がる)
     |         |     Q  = E より 1 位相遅れ
     |         |     * 待ち (mem_pend, settle, XLINK の窓, ディスク (同期モードのとき), ACIA, 電源) があると
     |         |       ph 0 で止まる: E のサイクルが延びる (CPU が止まる)
     |         |     |
     |         |     +--> ecyc (E のサイクルごとに 1 クロックのパルス)
     |         |           +--> timer_rtc.v: **2026-11-08 から E ではなくシステムクロックの 32 クロックごとのパルス `rt_ecyc` を数える** (tick 50 Hz = 42188 パルス、時計 1 秒 = 2109375 パルス。9.13)
     |         |                (止まっている間は数えない: PSRAM の待ちで時計は遅れる)
     |         |
     |         +-- Z80 のクロックイネーブル cen_raw: cnt = 0..8 の 9 クロックごとに 1 回 = 7.5 MHz   [z80_sub.v]
     |         |     * メモリのアクセスの間は zstall で止まる (読み出し 27 クロック、書き込み 18 クロック)
     |         |     * upd (cnt == 4): バスのレジスタを更新する (マルチサイクル制約 matenro.sdc)
     |         |     |
     |         |     +--> XE_CLK: 有効になった Z80 のクロックの数
     |         |
     |         +-- XLINK のマイクロ秒カウンタ XE_US: 135 クロックで 2 us (半分の 67.5 クロックで +1 us)  [xlink.v]
     |         |     * 止まらない実時間 (6809 が止まっても進む)
     |         |
     |         +-- UART (acia_uart.v): BAUD_DIV = 586 -> 115200 baud
     |         +-- SD の SPI (sd_disk.v): 初期化 264 kHz (半周期 128 クロック) -> 動作中 11.25 MHz (半周期 3 クロック)
     |         +-- PSRAM コントローラ (psram_controller.v): clk81 で動く。1 アクセスは約 19 クロック
     |         +-- ボタン (btn_toggle.v) のデバウンス、LED のハートビート、起動時のリセットの長さ (por)
     |
     +--> clk81p 67.5 MHz, clk81 より 90 度 (3.7 ns) 遅れ
               +--> ODDR -> O_psram_ck (PSRAM の CK)
```

| クロック | 周波数 | 作り方 | 用途 |
|---|---|---|---|
| `sys_clk` | 27 MHz | 水晶 | PLL の入力だけ |
| `clk81` | 67.5 MHz | rPLL | すべての論理 (名前は 81 MHz 時代の名残) |
| `clk81p` | 67.5 MHz (+90°) | rPLL の CLKOUTP | PSRAM の CK の ODDR だけ |
| E / Q | 1.875 MHz | `clk81` を 9 クロックの位相で分割 (止まることがある) | 6809 (MC6809 コア) |
| Z80 クロック | 7.5 MHz | `clk81` の 9 クロックごとのイネーブル | TV80 (止まることがある) |
| 8088 (予定) | 7.5 MHz 前後 | 同じイネーブルの作り | まだ FPGA にない |
| タイマ tick | 50 Hz | E のサイクルを 37500 数える | OS-9 の時計 |
| UART | 115200 baud | `clk81` / 586 | コンソール |
| SD の SPI | 264 kHz / 11.25 MHz | `clk81` / 256 と / 6 | SD カード |
| XE_US | 1 MHz (カウンタ) | `clk81` の 67.5 クロックで +1 | `etime` の時間 |

**タイミング解析 (Gowin のレポート)**: `clk81`、`clk81p`、`E`、`Q` を `create_clock` / `create_generated_clock` で宣言し (`SIM09/constraints/tn9k.sdc`)、`clk81` と `E` `Q` の間は false path (CPU が使う時刻は `clk81` 側が静かなときだけ)。Z80 のコアの内部は 9 クロックのマルチサイクル、バスのレジスタとの間は 4〜5 クロック (`fpga/tn9k/constraints/matenro.sdc`)。レポートの「Fmax」は `clk81` の値 (今は 69.6 MHz、67.5 MHz に対して最悪スラック +0.451 ns) を見ます。`E` の Fmax (23 MHz) は E の制約 (1.875 MHz) に対するもので、意味のある余裕ではありません。

**時間の流れ方の違い** (シミュレータの `-hw` の元): 実時間 (`XE_US`) は `clk81` で進み、止まらない。6809 の E とタイマと Z80 のクロックは、PSRAM などの待ちで止まる。そのため、OS-9 の時計は実時間より遅れる (待ちが多いほど)。

### 9.10 割り込み線の系統図 (2026-11-04)

6809 の `nIRQ` / `nFIRQ` と、Z80 (TV80) の `int_n` / `nmi_n` が割り込み線のすべてです (6809 の `nNMI` は 1 に固定)。`nIRQ` には、図のタイマとクロスリンクのほかに、コンソール ACIA の割り込み `acia_irq` (`acia_uart.v`、9.11) と、ディスクの非同期モードの終了割り込み `disk_irq` (9.12) も OR されます。図では省いています。すべて `clk81` に同期した信号で、割り込みの線に非同期の入力はありません。

```
  matenro_soc.v                      xlink.v (soc/sub/xl)                         z80_sub.v (TV80)
  --------------------------      -----------------------------------      ---------------------------------

  timer_rtc.v                       c_ien, c_firq <- XCTL ($FFCA) bit4, bit3
    pending: tick 50 Hz で 1           |
    0 に戻る: iack                     |        Z80 の OUT $02 (s_port 2)
    (cpu_bs & !cpu_ba)                 |                 |
        |                              |                 v
     timer_irq                         |            pend_s2m (XSTAT bit0)
        |                              v                 |    0 に戻る: 6809 が XSTAT に書く (ACK)
        |             irq_n_o = pend_s2m & c_ien & ~c_firq --> xl_irq  --+
        |             firq_o  = pend_s2m & c_ien &  c_firq --> xl_firq --|--+
        |                                                                |  |
        +--> nIRQ  = ~(timer_irq | xl_irq | acia_irq)  <----------------------------+  |      (FREERUN = 0)
             nFIRQ = ~xl_firq               <-------------------------------+
                |
                v
           mc6809i --> IRQ ベクタ --> OS-9 のカーネル --> D.SvcIRQ (Clock) --> D.Poll --> xlink ドライバ


                                    6809 が XID ($FFCC) に書く
                                      | bit7 = 0              | bit7 = 1
                                      v                       v
                                 pend_m2s (XSTAT bit1)    sub_nmi (1 クロックのパルス)
                                      | sub_int                 |
                                      |   0 に戻る:             v
                                      |   Z80 の OUT $03     nmi_pend (次の cen まで保持)
                                      |   (s_port 3, ACK)       | nmi_n <= ~nmi_pend
                                      v                         v
                              .int_n(~sub_int)           .nmi_n(nmi_n)  --> TV80
```

* **IRQ の合成**: タイマと XLINK の OR は `matenro_soc.v` の `mc6809i` のポート接続の 1 か所だけです。`FREERUN = 1` (v09 のモニタ ROM) のときだけタイマが FIRQ になります。
* **XLINK の IRQ / FIRQ** は、レジスタ 3 つ (`pend_s2m`、`c_ien`、`c_firq`) の AND で、組み合わせ論理は 1 段です。
* **Z80 の INT** は `pend_m2s` のレベルをそのまま渡します。ACK するまで立ち続けるので、TV80 が `cen` の立ったクロックでしか見なくても取りこぼしません。NMI は XLINK が 1 クロックのパルスしか出さないため、`z80_sub.v` の `nmi_pend` が次の `cen` まで保持します。
* 8088 は FPGA にありません。シミュレータは Z80 と同じ構造です (`SUB_INT`、`SUB_NMI`: DESIGN.md 7.1)。

### 9.11 コンソール ACIA の割り込み (2026-11-06)

`new-sbc09` が 11/5 に、コンソール ACIA に 6850 の制御レジスタと割り込みを入れ (`acia_uart.v`: 受信割り込み RIE、送信割り込み TIE、マスタリセット、状態ビット 7 = IRQ、送信 FIFO 15 文字)、OS-9 の端末ドライバを割り込み駆動にした。`acia_uart.v` は `new-sbc09` のものを共有しているので、Matenro の SoC (`matenro_soc.v`) も合わせる必要があった (合わせないと、新しいポート `wr_ctl`・`cdata` が接続されず、割り込みが動かない)。

* `$E000` への書き込み (制御レジスタ) を `acia_cwr`・`acia_cbyte` で `acia_uart` に渡す。
* `acia_irq` を CPU の `nIRQ` に、タイマ (`timer_irq`) とクロスリンク (`xl_irq`) と OR でつなぐ (`FREERUN` のときは ACIA だけ)。IRQ 線は 3 つの源の OR になった (9.10 の図の `nIRQ` に ACIA が加わる)。
* モードレジスタ (`$E00E`) への書き込みで、ACIA の割り込みを止める (制御レジスタに `03h`: マスタリセット)。`new-sbc09` と同じ。
* 確認: `fpga/tn9k/sim` の Verilator で、既存の `xltest` が通る (13BA 0037 1D4C) こと、新しいテスト ROM `fpga/tn9k/test/aciirq.asm` (`make ROM=aciirq TV80=…`) で、送信割り込み (TIE) の状態ビット 7 が立ち、IRQ が 1 回入り、マスタリセットで消えること (出力 `S B I R P`)。受信割り込み (RIE) は共有の `acia_uart.v` の中の判定で、`new-sbc09` 側で確かめられている。
* **`reboot`**: `new-sbc09` の `reboot` コマンドは電源レジスタ (`$E00F`、Level 2 は `$FF8F`) に `$A6` を書く。Matenro の `reboot` は `$A7`。どちらも `reboot_r` を立てて、リセットボタンと同じ再起動にする (`matenro_soc.v`、シミュレータ `src/machine.c` も同じ)。以前の `$A6` = 終了 (コード 1) は廃止した。
* **コマンド名**: Matenro の C のプリプロセッサは `cpp80` (`new-sbc09` の C コンパイラの `cpp` と名前がぶつかるため)。`cc80` が `cpp80` を呼ぶ。
* ビットストリーム (起動 ROM 版、`TAG=_acirq TV80=… scripts/build.sh boot`): LUT 約 7100、CLS 94%。**`clk81` の Fmax 69.1MHz (目標 67.5MHz)、負のスラックなし** (`$A6` の再起動を入れた版)。
* **実機 (Tang Nano 9K、2026-11-06)**: このビットストリームを SRAM に書き (`openFPGALoader -b tangnano9k`)、`mkdisk.sh` で作り直した SD イメージ (割り込み駆動の端末ドライバの OS-9 Level 2) で、OS-9 が起動して `OS9:` が出た。`sleep 1000` を `^C` で止めると `Error #003` ですぐ戻る。`dir /d0/cmds` に `new-sbc09` の `cc` `cc1` `cpp` `reboot` と Matenro の `cpp80` `cc80` `cpm` `xrun` が並ぶ。**`reboot` (`$A6`) で `Rebooting...` のあと PSRAM の検査と OS-9 の起動が再び走った**。`load xlink`、`load x0`、`cpm /d0/hello.com abc` が `Hello from CP/M-80 on the Z80` / `!` / ` ABC` を出した。`cpp80` も動く。**フラッシュにも書いた** (`openFPGALoader -b tangnano9k -f`)。USB を抜き差しして電源を入れ直しても、フラッシュから同じ版で起動し、`reboot` (`$A6`) と `cc80 -t=/d1/htc -r hello.c` (`cpp80` → Z80 の HI-TECH C) が動いた。`duo` (6809 が 18 行、Z80 が 7 行、5.8 秒) と、`mandel.c` (`etime` で 186.7 秒、シミュレータの見積もり 183.7 秒) も動いた。

### 9.12 ディスクの非同期モードと XLINK のアドレス移動、起動メッセージ (実機で確認、2026-11-08)

sim09 が 11/7 に入れた非同期ディスク (制御・状態レジスタ `$E049`、Level 2 は `$FFC9`) と、Matenro の XLINK の `XCTL` が同じ番地で、sim09 の新しい OS-9 Level 2 `PDisk` が使うと Z80 のリセットや IEN の消去が起きた (`make test-mh` が 3 件失敗した)。**XLINK を `$FFCA`-`$FFCE` (Level 1 は `$E04A`-`$E04E`) へ 1 つずらして**解消した (ドライバ、`duo` `cpm` `etime` `xrun`、RTL のデコード、シミュレータ、試験、文書)。

* **RTL**: `psram_arb4.v` に最低優先のマスタ 4 (ディスクのバイト読み書き)。`matenro_soc.v` に `$E049` の状態 (bit7 終了、bit6 割り込み許可、bit1 非同期、bit0 処理中)、終了割り込み `disk_irq` (IRQ に OR)、命令を書いた時点のメモリマップの保持 (`dm_blk0/1`)、非同期のあいだ 6809 を止めない `disk_hold`。同期モードの `disk_sel` の切り替えは不要になった。リセットとモードレジスタの書き込みで同期に戻る。
* **シミュレータ**: `src/machine.c` に同じ動き (読み 800、書き 7500 サイクル。`-v` のときは同期のまま)。
* **試験**: `make test-mh` (53 件、失敗 0)。RTL は `make -C fpga/tn9k/sim ROM=disktest TV80=…` が sim09 の `disktest.s` を `a09` で組んで流し、5 項目 (同期の読み、非同期の読み、CPU と DMA のメモリ共有、割り込み、非同期の書き) が通る。
* **資源**: Logic 7,835 (91%)、CLS 4,138 (96%)、レジスタ 2,284、BSRAM 8。`clk81` の Fmax 67.528MHz、負のスラックなし (docs/FPGA_RESOURCES.md)。
* **起動メッセージ**: メモリ検査の見出しを `Matenro Memory ` にした。OS-9 の起動ルーチン (`sysgo`) は `startup` を読まない構成なので、OS の側では出せない。行頭の `Matenro` で、素の sim09 の板と見分ける。
* **実機 (Tang Nano 9K)**: フラッシュに書いて起動し、`Matenro Memory >>>… OK 2048K` から OS-9 Level 2 が起動した。新しいカードのイメージ (`matenro_card_async.img`、`mkdisk.sh` + `bigd1.sh`) で `free /d1` は 262,144 セクタ (空き 260,113)、`load xlink` `load x0` `duo` が通った (6809 が 18 行、Z80 が 7 行、5.78 秒)。`libc.lib` のコピーを繰り返す 35 秒ほどの間に OS-9 の時計が約 13% 遅れた (同期のときの前回の測定は 24%)。残る遅れは PSRAM の取り合いとみている。電源の入れ直しからの起動は未確認。
* **古いカードのイメージ**: XLINK のドライバが `$FFC9` を見る古いイメージ (2026-11-07 以前の `matenro_card*.img`) は、このビットストリームでは `duo` `cpm` `cc80` が動かない。`mkdisk.sh` と `bigd1.sh` で作り直す (README と MANUAL の手順のとおり)。

### 9.13 タイマと時計を実時間にする (実機で確認、2026-11-08)

OS-9 の時計は、CPU が PSRAM からコードを実行している間、実時間より遅れていた。`timer_rtc.v` が CPU の E サイクル (`ecyc`) を数えるのに、PSRAM を待つ間は E のサイクルが 36 クロックより長くなるため。実機で測ると (`dhry`、ディスクも Z80 も使わない): OS-9 の時計で 10 秒のあいだに 2040 回 (実時間は約 12 秒。時計は約 84%)、`libc.lib` のコピーを繰り返す間は約 13% 遅れていた。待機 (`SYNC`、PSRAM を触らない) のあいだは正確だった。

* **対策**: タイマに渡す `ecyc` を、自走カウンタ `hb` の下位 5 ビット (32 クロックごと) から作ったパルス `rt_ecyc` にした (`matenro_soc.v`)。tick は 50 Hz = 42188 パルス (誤差 0.001%)、1 秒 = 2109375 パルス。同期モードのディスクが CPU を止めているあいだ (`disk_hold`) は、パルスも止める (割り込みを受けられないあいだの tick は、いずれにせよ落ちるため)。`sim09` の `timer_rtc.v` は変えていない。
* **シミュレータ**: タイマと時計 (`$E031` の日時) を `total_cycles` に `stall_ps` (`-hw` の待ち) を足した時間で進める (`timer_now()`)。`-nohw` は従来どおり。
* **資源**: Logic 7,864 (92%)、CLS 4,142 (96%)、レジスタ 2,285。`clk81` の Fmax 68.599MHz、負のスラックなし。増えた回路は、5 ビットの比較と 1 FF だけ。
* **実機の結果**: `dhry` の窓 (実時間 26.5 秒) で OS-9 の時計は 26 秒、コピー 8 回 (実時間 約 37.8 秒) で 38 秒。遅れは消えた。`dhry` は時計 10 秒のあいだの回数が 1700 回に減った (時計が速くなったため)。`make test-mh` 53 件、Verilator の XLINK、`disktest` 5 項目、`aciirq` が通る。
* **副作用**: OS-9 のタイムスライスと `sleep` も実時間になる。CPU が PSRAM を待つ分、1 tick のあいだに実行できる命令が減る (約 16%)。これは遅れが隠れていただけで、板の実際の速さは変わっていない。

### 9.14 Tang Nano 20K 版 (6809 + 8088、2026-11-12。実機で動いた: TN20K.md の 8 章)

20K のボード向けの設計は [TN20K.md](TN20K.md) に書きました。この SoC (`matenro_soc.v`) を `` `define SUB8088 `` で 8088 (MCL86) 版にし、PSRAM のかわりに SDRAM コントローラ (`sdram_ctl.v`) をつないだものです。9K の SoC への変更は、サブ CPU の選択 (`ifdef`)、`xlink.v` の `SMMU_WT` (GW2A の BSRAM のため。9K では 0) だけで、9K の回路は変わりません。ビットストリームは 54 MHz で Logic 38%、CLS 48% で通りました (67.5 MHz は MCL86 のマイクロコード ROM の経路で通らない)。
